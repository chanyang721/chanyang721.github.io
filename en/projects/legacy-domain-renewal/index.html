Project Overview

I redefined goal and content boundaries between Attale and Attale Pro

The core challenge was keeping Attale's user goal execution flow and Attale Pro's recommended-goal and content management flow from becoming mixed in the same data structures.

Within the backend renewal scope, I analyzed the legacy structures of both services and separated curated originals, user goal instances, the goal → task → daily hierarchy, eight life areas, and the hashtag and content graph. I migrated operational content from CSV/Notion into the new table structure and documented the Express/TypeORM APIs together with evidence of an operational transition based on S3, Swagger, and Docker.

  • I redesigned the shared data boundaries around Attale's user goal execution and scheduling flow and Attale Pro's recommended-goal and content management flow.
  • Curated goals remain as originals, while goals started by users become separate instances with individual progress states.
  • I separated starting a goal through copying from simply saving content through a link, distinguishing access to current originals from the ability to edit a personal copy.
  • I separated the publicly shareable evidence of cleaning and migrating source content comprising approximately 307 recommended goals, 1,052 tasks, and 81 articles.

  • Established foundations for the operational transition, including authentication, S3 uploads, Swagger documentation, and Docker/ECR deployment scripts

Constraints

Constraints to address first

  • Attale for consumers and Attale Pro for experts and operators used the same goal and content data, but differed in who edited it and how it was used.
  • Operator-edited curated originals and personal goals that users pursued and edited could not share the same lifecycle.
  • Starting a goal and saving content for later had different storage costs and requirements for staying current.
  • The eight life areas and detailed categories needed to be managed as operational data rather than code enums.

Phase 01 · Attale & Attale Pro Data Boundaries

Attale & Attale Pro Data Boundaries

Phase 01

I separated the data lifecycles of consumer-facing Attale and expert-facing Attale Pro

Although they may look like the same goal, a recommended goal managed in Attale Pro and a goal a user actively pursues in Attale differ in who edits them, how current they need to be, and when they are deleted.

  1. 01

    Requirements Analysis

    Attale Pro manages recommended goals, articles, and videos; Attale users bring these into personal goals and add their own schedules and progress states.

    • If user edits altered the original template, incorrect content could spread to other users.
    • User goals needed individual state such as duration, budget, completion status, and child tasks.
  2. 02

    Domain Modeling

    I separated curated goals, articles, and videos as original content from user goals and saved content as user data.

    • Operators manage original content, which multiple users reference.
    • User data has its own owner, progress state, deletion status, and subordinate plans.
  3. 03

    Architecture Decisions

    Instead of mixing original content and user data in one table with a status field, I separated them into copying and linking paths.

    • Editable goals require copies, while bookmarks intended to show the latest original need only a link.
    • This distinction became the basis of the subsequent template-to-instance model.
  4. 04

    Implementation & Verification

    The archived entities and ADRs show curated originals, user goals, and user-to-content link models.

    • I distinguished active entities from commented-out design files to recheck what was actually implemented.
    • Service names are used to explain the scope, but internal API paths and operational data were removed from public copy.
  5. 05

    Operations & Recovery

    When data becomes inconsistent, the first step is to distinguish whether the original content changed, the user's copy changed, or only a link remains.

    • Without that distinction, an operator's edit to an original could unintentionally affect user goals.
    • Deleting user data must have different recovery criteria from deleting original content.
