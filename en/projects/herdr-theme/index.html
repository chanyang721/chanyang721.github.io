Herdr Multi-Agent Workspace Sidebar Theme

A public theme for the open-source terminal app Herdr that brings the status of multiple coding agents, shared projects and message routes across computers, and plan usage limits into one sidebar. I drew the boundary so the UI only displays the observations it receives while work decisions stay with external tools behind a file contract, and I moved 97 Python helper files into a single Rust executable.

Project Overview

It started from wanting to see “who is doing what” on one screen while running several coding agents in terminals

When agents such as Claude Code and Codex run in separate Herdr panes, it is scattered which pane is working, which is waiting for a human answer, what messages flow to other computers, and how much plan limit remains.

herdr-theme is a Herdr layout and theme that gathers this information into one sidebar and the pane headers. It provides per-computer agent counts and shared projects, unread messages and message-route animations, per-pane model, reasoning effort, and session usage, CPU/RAM, MCP connections, CLI sign-in and plan limits, plus project document search and a document tab.

The UI is split into JavaScript mods, while helpers for installation and updates, documents, collection, and voice live in the Rust executable herdr-theme. The theme does not make decisions such as task allocation, acceptance, or cleanup; it only reads and displays local feed files written by an optional external producer.

Ownership

My direct responsibilities

  • Designed and implemented the sidebar, pane header, and monitor strip mods, plus the layout and color themes, running on the Herdr app
  • Defined a versioned feed written by external producers, along with a display-only lifecycle contract and JSON schema, so the UI never guesses task state
  • Designed local integration extension points that hand question and permission card buttons off only through a request file, a configured command, and a receipt
  • Ported 97 Python helper files to the Rust executable herdr-theme, using frozen original outputs and a mapping to the original tests as the baseline
  • Analyzed how bystanders’ speech leaked into voice dictation and got sent, and blocked it with a submit-time check hook
  • Built CPU guard tests that statically check mod timers, and an Ubuntu, Windows, and macOS CI matrix

Constraints

Constraints to address first

  • Herdr is an upstream open-source app, so the theme had to work only within mods, layouts, and external executables, without modifying the app or core.
  • The core events needed for message animations depend on an upstream PR I proposed that is still open, so I could not assume standard releases emit them.
  • Because the repository is public, per-machine paths, accounts, and personal settings had to stay out of code and media, separated into git-ignored *.local.json files.
  • As periodic timers and polling in the sidebar mods grow, simply keeping the window open costs CPU, so every timer had to be treated as a decision.
  • Build tools, audio, and rendering differ across macOS, Windows, and Linux, so verification scope had to be recorded per platform.

Phase 01 · Display-Only Lifecycle Contract

Display-Only Lifecycle Contract

Phase 01

A finished response is never shown as “task complete”

The sidebar shows allocation, work, review, acceptance, retention, and cleanup. If the UI guessed state from progress or the end of a response, work with remaining tasks could look complete and a pane still open could disappear as if closed.

The theme receives the feed’s task stage (stage 0–5) and the pane’s observed state (status · state) separately and draws both. Working, idle, needs-human, unseen-result, cleanup-wait, closing, and closed are distinct states, and no new state is derived from issue numbers, role names, progress, or elapsed time. A row is removed only when the producer confirms closing step 4; state: closed alone does not remove it.

The feed is read up to 2 MiB and reported as ready, missing, or invalid. Interrupted writes and read failures keep the last valid display, and commands contained in a feed are never run. Navigation uses only the space and pane targets the feed names explicitly; targets are never guessed from opaque IDs.

Display producer evidence as is instead of inferring state

Choice

Task stage and pane state are separate fields, and row removal is tied only to closing step 4 as confirmed by the producer. Even an accepted task keeps its row while the pane remains.

Problem
A finished response, a full progress bar, a sent message, or an expired countdown was not evidence of actual acceptance or cleanup.
Rationale
When the UI guesses wrong, the user misses remaining work. Keeping the judgment with the side that holds the evidence lets the theme mean the same thing with any producer.

Trade-offWithout a feed, task trees do not appear and only the basic sidebar remains. If the producer stops updating, stale rows can remain, so the update responsibility moves to the producer.

Outcome

Verifiable outcomes

  • Released a sidebar, pane header, monitor strip, and document tab layout for Herdr 0.1.11+ as an Apache-2.0 public repository, with Rust install and update commands that preserve existing settings
  • Implemented a display-only feed contract and JSON schema separating task stage, pane state, and closing stage, plus display of seven pane states
  • Removed 97 Python helper files and replaced them with one Rust executable, keeping a per-file inventory and frozen original outputs as the regression baseline
  • Blocked voice dictation submissions without verification evidence using a submit-time check hook and headset-only automatic submission (macOS)
  • Automated checks for CPU cost structure and per-platform regressions with static mod-timer checks and a four-runner CI

Limitations

Limitations and unimplemented scope

  • The core events used by message animations depend on an upstream PR (herdr-core #167) that is still open as of 2026-11-24, so standard releases need a compatible adapter or local collector.
  • Linux supports only the native helper; its desktop UI has not been verified. Voice and HTML snapshots are macOS-only.
  • The README workflow GIF and gallery are edited captures of synthetic data, not recordings of real end-to-end work. The weekly timeline feature does not yet have a fresh native capture.
  • Task trees, cards, and reports appear only with a separately configured external producer; theme installation includes no task service.
  • Speaker verification figures come from offline evaluation on public speech and synthetic conditions, not real-world accuracy.
  • The large lifecycle and installer modules and domain-specific IO facades remain as structural debt to refactor, and there are no recorded before-and-after CPU usage measurements.
