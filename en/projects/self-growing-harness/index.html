Self-Improving Multi-Agent Harness

A study in which I built and operated a personal self-improving multi-agent harness and used real operating data to judge which agent limitations engineering can reduce and which are irreducible. After the bash-based v1 stopped in 2026-06, I rebuilt it on the Herdr terminal app starting in 2026-10, and I still use it today to split work across multiple Claude and Codex sessions by difficulty and have a model from a different family than the author cross-review the results.

Project Overview

I began by asking how judgments made while working with agents could compound over time

The starting problem was that decisions, trial and error, and lessons learned while working with AI disappeared at the end of each session, leading to the same mistakes in subsequent tasks.

v1 (2026-05–06) was a runtime that ran role agents such as strategy, implementation, and QA in parallel in split macOS terminal panes. A bash router aggregated each worker's output (outbox) to detect knowledge gaps, while memory and knowledge subsystems accumulated and distilled those judgments and injected them into later tasks.

Initially, the memory system was introduced only declaratively and never connected to actual execution, leaving it largely inert. I therefore redefined the harness as a runtime that repeatedly produces, structures, and reuses judgments rather than a framework for accumulating features. This research case documents the structural agent limitations observed in that process.

The structure I use now (2026-10–) runs on the Herdr terminal app. Multiple Claude and Codex sessions stay open in fixed per-project workspaces, and a task allocation session tags each piece of work with a difficulty tier and sends it to an idle session or opens a new session with that tier's model. A review session from a different model family than the author judges each work session's report, and tasks, reports, verdicts, and acceptances all remain as immutable records that are injected back as context and reference cases for later sessions.

Nature of the Research

This is not a controlled benchmark. It consists of natural experiments and before/after intervention comparisons observed while running the harness on actual projects. These methodological limitations are stated explicitly at the end.

Ownership

My direct responsibilities

  • Defined disappearing judgments and the declaration≠execution disconnect as the problem, reframing the repository from a collection of settings into a runtime that accumulates judgments
  • Separated the self-improvement loop into detection (automated in code) and mutation (human-gated), making the safety boundary explicit
  • Structured limitations observed in actual project operation into a taxonomy distinguishing limitations reduced through engineering from irreducible limitations
  • Designed allocation policies for providers, model tiers, and reasoning depth (effort) based on role complexity, cost, and benefit
  • Discovered and documented a routing gap in code between configured model capability and actual application (intent≠application)
  • After v1 stopped, rebuilt the harness on Herdr so that task allocation, cross-review, acceptance, and session cleanup are decided on top of immutable records
  • Encoded rules that choose the model family and session by task difficulty tier and remaining usage, and that require review by a model family different from the author
  • Shifted the main path of the learning loop from an approval pipeline to "reuse of unverified reference cases + filtering by the outcomes of their use"

Constraints

Constraints to address first

  • Because these were observations during actual operation rather than a controlled benchmark (n>1, control), figures had to be presented only as natural-experiment observations and self-measurements.
  • Model IDs and provider policies depend on the point in time, so I needed to state the observation date.
  • I needed to show plainly that mutation is blocked by a human gate, without overstating the system as autonomous self-improving AI.
  • I needed to center the findings about limitations rather than list system size, such as subsystem or role counts, as achievements.
  • Because multiple sessions run at once on two computers (Windows and macOS), I had to update the harness without interrupting running sessions and keep records from conflicting with each other.
  • Because cross-review can stop when one model family runs out of usage, I needed a rule that same-family substitute reviews do not count as grounds for acceptance.

Phase 01 · Separating Detection from Mutation

Separating Detection from Mutation

Phase 01 · Self-Growth Loop

I automated detection in code and placed mutation behind a human gate

Separating self-improvement into detection and mutation is the core safety boundary. Detection is automated, but mutations that actually change memory must pass human ratification.

  1. 01

    Detection Automated in Code

    When a worker leaves markers such as [KNOWLEDGE_GAP] in its outbox, the router increments counters. clo-trigger-check scans for thresholds (K3=3, K4=5) being exceeded and automatically records the result in the CLO inbox.

  2. 02

    Mutation Ratified by a Human

    Mutations that actually change memory (brain) are permitted only after CLO consolidation, human ratification, and a sentinel. Without the sentinel, the PreToolUse hook blocks the edit itself.

  3. 03

    Why I Drew the Boundary Here

    Automatically overwriting memory can silently accumulate incorrect learning, and humans may miss validation failures in self-referential governance. I therefore fixed the maturity boundary at detection by code and mutation through a human gate.

Do Not Make Mutation Autonomous

Choice

I automated only detection and escalation in code; brain mutation requires CLO consolidation, human ratification, and a sentinel.

Problem
When detection signals exceed thresholds, the system can automatically generate improvement candidates.
Rationale
Automatically overwriting memory can silently accumulate incorrect learning, and humans may miss validation failures in self-referential governance.
Safeguards
  • The PreToolUse hook blocks brain edits without a sentinel
  • Mutations prioritize appending; unauthorized deletion is prohibited

Trade-offHuman involvement is a bottleneck compared with full autonomy, but it preserves a clear, safe maturity boundary.

An Honest Account of Maturity

Detection is automatic, but mutation is deliberately nonautonomous. I do not call this autonomous self-improving AI.

Behind the Screen

What the harness does behind the Herdr Theme screen, in the same stage order

In the same order as the Herdr Theme card’s workflow replay (assign → message → review and acceptance → apply → cleanup), this explains what the harness decides and records behind each scene on the screen. The theme only reads feed files and draws them; the decisions sit on this harness side. Each stage carries one theme capture as evidence.

  1. 01 Allocation

    Choose Sessions by Difficulty Tier

    The dispatch session tags each piece of work with a difficulty tier and sends it to an idle session, or opens a new session with a model of that tier. The chosen model and the reason stay in the dispatch record, and the theme draws the new row only after that result reaches the feed.

  2. 02 Message

    Hand-offs between sessions and reports

    Passing things between sessions used to be done by a person. Now a work session’s report goes to a review session, and tasks and reports stay as records that cannot be edited. The theme’s message lines are routes drawn from the sender and receiver records.

    Theme screen 03 How messages travel →Theme screen 04 Alerts per space →Theme screen 05 Ask for confirmation →

  3. 03 Review and acceptance

    A different model family reviews, and acceptance is decided from records

    A model family different from the author reviews the work, and only each reviewer’s last verdict counts. Any HOLD or CONDITIONAL blocks acceptance, and only a PASS from the other family is accepted by machine policy. The «in review → awaiting acceptance» cells on a theme row are this verdict as written to the feed.

  4. 04 Apply

    Accepted results and their records

    Tasks, attempts, reports, verdicts, and acceptance stay in per-machine append-only records, and the summaries for the screen are generated from those records. The PUSH, CI, and CD cells of the theme’s repo rows are filled only with values in the records and collected results.

    Theme screen 07 Commit → PUSH → CI → CD →

  5. 05 Cleanup

    Fail-closed session cleanup

    Only sessions that finished an accepted task are closed, after the conditions are checked again right before closing; if anything is unknown, the session stays open. The theme shows the closing stages that passed this check and removes only finished rows.

Outcome

Verifiable outcomes

  • An operational taxonomy distinguishing reduced from irreducible agent limitations (2 reduced / 1 partial / 2 irreducible)
  • Bootstrap Paradox — identified an irreducible human-in-the-loop floor in self-referential governance
  • Derived a model-capability allocation policy: judgment=claude/parallelism; execution=codex/model depth
  • Intent≠application gap — discovered in code that routing can nullify configured model capabilities
  • Expressed the actual boundary of self-improvement without exaggeration: detection=automatic, mutation=human-gated
  • Current structure — encoded a cross-review flow in which a model from a different family than the author reviews and acceptance follows the aggregated verdicts
  • Current structure — kept tasks, reports, verdicts, and acceptances as immutable records, so session cleanup and learning are decided on the same records
  • Current structure — shifted the learning loop to "reuse of unverified cases + filtering by the outcomes of their use" (off by default; effect not yet measured)

Limitations

Limitations and unimplemented scope

  • This is an n=1 self-report study. There is no control group, and the observer is also the operator, limiting generalizability.
  • Figures such as a functioning rate of 15%→60%, tokens down 71%, and 5 of 29 are operational observations and self-measurements, not controlled evaluations.
  • Model IDs (Opus/Sonnet/Haiku) and provider policies are as of 2026-06, and the current structure's per-tier model mapping is also time-dependent. Allocation judgments change as model generations change.
  • Many v1 subsystems (the governance and knowledge-distribution layers) are not yet connected to the new structure, and the import gate's effectiveness has not been verified.
  • I have not tallied how many defects cross-review actually caught or how cleanup delays changed. Independent review stops when one model family runs out of usage.
  • Case-reuse learning is off by default, and use outcomes are sessions' self-reports, so its effect has not been measured yet.
