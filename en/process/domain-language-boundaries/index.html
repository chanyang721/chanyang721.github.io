Process Evidence · 02

Establish domain language, boundaries, and state models

I defined boundaries and state models so terms such as payment, billing, course access, subscription, refund, and points would have consistent meanings across code and documents.

I divided the system by domain objects and state transitions—Order, PaymentIntent, Payment, Entitlement, Subscription, and Ledger—rather than by features.

How I worked

Actual Working Approach

  1. Input

    I collected recurring nouns from requirement documents, the existing database, and payment and subscription code, state-change points with different lifecycles, and dimensions such as language and currency that change with global expansion.

  2. Questions to ask

    I checked whether current state was mixed with historical facts, whether external side effects ran before internal intent was recorded, and whether access rights were treated as an incidental order field.

  3. Output

    I established a domain model separating purchases, billing cycles, payment attempts, actual payments, course access, the ledger, and pending/final states.

Detailed work example

Separating authorization, affiliation, review, and categories into distinct domains

In a private B2B platform, I separated Company, Vendor, UserAffiliation, UserRole, CertificationRequest, TaxCategory, and UICategory. The model allowed one user to have affiliations and roles in multiple organizations, with separate approval lifecycles for company, vendor, and employee verification. A later audit separately recorded where this model intent diverged from actual code contracts.

Input
I extracted recurring nouns, states, and approving actors from actor-specific plans and verification, authorization, and category requirements.
Boundaries
I separated account identity, organizational affiliation, domain-specific roles, verification requests, tax categories, and display categories into models with different reasons to change.
State model
I treated company, vendor, and employee verification as separate pending facts with request, approval, and rejection histories, rather than as current affiliation information.
Output
I then organized APIs and the database around Identity, Affiliation, Certification, and Taxonomy boundaries rather than screen menus.
Audit
The employee-approval flow shows an intent to create affiliation and roles in one transaction. However, entity/service field mismatches and authorization-guard contract mismatches prevent me from presenting it as a completed RBAC case.
Verification criteria

Documenting each model's invariants alongside its name

Instead of disclosing every table column, the portfolio describes the questions each model must answer and the conditions it must never violate at a level suitable for public disclosure.

Payments and subscriptions
I assigned purchase intent to Order, billing cycles to Invoice, gateway attempts to Intent, and actual authorization results to Payment.
Points and ledger
I separated Accrual as the payout commitment, Ledger as append-only evidence of changes, and Wallet as the current-balance snapshot.
Global presentation
I separated classification codes and locale-specific names, terms translations, payment currency, and notification-message selection so UI language and server-side canonical data would not be mixed in one model.
Disclosure scope
I explain design decisions through responsibilities, state transitions, and invariants, rather than disclosing complete internal table schemas.
