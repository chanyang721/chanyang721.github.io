  • 포인트 회계, 추천인·보상, 티어 정책, 결제, 커뮤니티 활동, 알림·정산 파이프라인의 경계 설계·구현

Constraints

먼저 해결해야 했던 제약

  • 지급 예정 포인트와 즉시 사용 가능한 포인트를 분리해야 했습니다.
  • 같은 이벤트나 정산 배치가 반복 실행돼도 포인트가 한 번만 반영돼야 했습니다.
  • 동시에 발생하는 적립·사용·환불이 사용자 잔액을 깨뜨리면 안 됐습니다.
  • 구매자, 추천인, 커뮤니티 활동자의 티어·보상 규칙을 운영 정책으로 변경할 수 있어야 했습니다.
  • FCM이나 알림 큐 장애가 결제·정산 결과를 되돌리면 안 됐습니다.

Project Overview

영상 강의와 커뮤니티 활동이 결제·보상·알림·정산으로 이어지는 교육·콘텐츠 서비스입니다

사용자가 강의 구매, 활동, 추천, 커뮤니티 참여를 반복할 이유가 필요했고, 동시에 보상이 언제 생기고 언제 쓸 수 있는지 자연스럽게 이해할 수 있어야 했습니다. 이 프로젝트는 특정 포인트 기능 하나가 아니라 포인트, 추천인, 티어, 커뮤니티, 결제, 알림, 정산·복구를 서로 다른 변경 이유를 가진 도메인으로 분리하고 다시 연결한 서비스 구축 작업입니다.

  • 사업 관점에서는 포인트·티어·추천 보상을 재방문, 구매 전환, 커뮤니티 참여, 추천 확산을 돕는 장치로 바라봤습니다.
  • 사용자 관점에서는 결제, 활동, 추천, 티어, 알림이 끊어진 기능이 아니라 “보상을 받고 확인하고 다시 쓰는 흐름”으로 보여야 했습니다.
  • 기본 도메인은 포인트 지급 예정, 불변 원장, 지갑 잔액, 추천 관계, 티어 정책, 결제 확정, 커뮤니티 이벤트, Outbox·NotificationDelivery로 구성됐습니다.
  • 운영 관점에서는 보상 정책, 추천 관계, 티어 기준, 결제 결과, 회계 기록, 알림 전달을 추적·검증·재처리 가능한 상태로 남겨야 했습니다.
  • 각 요구사항은 확장성과 유지보수성을 위해 정책으로 바꿀 기준, 절대 수정하지 않을 회계 기록, 실패 후 재처리할 비동기 상태를 분리해 모델링했습니다.

01 · Problem Framing

기능 요구를 회계 규칙과 불변 조건으로 바꿨습니다

초기 요구는 “활동·구매·추천에 따라 포인트를 지급한다”는 기능 수준이었습니다. 이를 실제 운영에서 깨지지 않는 상태·제약·실패 시나리오로 재정의했습니다.

  • 지급 예정과 사용 가능 잔액은 분리한다.
  • 모든 잔액 변경은 수정되지 않는 원장으로 남긴다.
  • 동일 이벤트·배치 재실행은 한 번만 반영한다.
  • 포인트는 만료일이 가까운 Lot부터 사용하고, 동일 만료일은 생성 순서를 따른다.
  • 환불은 원결제에서 실제 사용한 Lot을 기준으로 복원한다.
  • 계정 전체 Freeze/Hold, 시스템 회계 계정, 유상 잔액 환불 청구처럼 더 큰 상태 관리는 1차 범위에서 분리하고, 현재 요구는 지급 대기·입금 대기 잠금·Lot 사용/복원으로 제한한다.
  • 알림 실패는 금전성 트랜잭션 결과에 영향을 주지 않는다.
설계 기준

AI는 누락된 예외와 대안을 탐색하는 보조 도구로 사용했고, 최종 결정은 PG 공식 문서, DB 제약, 코드와 테스트를 기준으로 검증했습니다.

02 · Accounting Model

Accrual–Ledger–Wallet로 지급 약속, 불변 기록, 현재 잔액을 분리했습니다

  1. 01

    Accrual

    “지급해야 한다”는 예약 기록입니다. availableAt, expiresAt, source, idempotencyKey와 취소 가능 상태를 가집니다.

  2. 02

    Settlement

    확정 시각이 지난 PENDING 적립을 선점하고 개별 트랜잭션으로 Ledger에 포스팅합니다.

  3. 03

    Ledger + Lot

    잔액 변경의 append-only 정본과 포인트 묶음의 출처·잔량·만료일을 기록합니다.

  4. 04

    Wallet

    사용자별 현재 잔액을 빠르게 조회하기 위한 스냅샷이며 Ledger 생성과 같은 트랜잭션에서 갱신됩니다.

두 가지 회계 경로

취소 가능·지연 확정 보상은 Accrual Flow를 사용하고, 결제 포인트 사용·환불·관리자 조정처럼 즉시 확정되는 거래는 Direct Ledger Flow로 처리했습니다. 기존 Asset·Wallet·Ledger·LedgerLot 모델은 유지하고, SYSTEM_LIABILITY·BREAKAGE 같은 시스템 회계 계정이나 독립 Points Service 분리는 규모·규제 트리거가 커질 때의 후속 범위로 남겼습니다.

관련 설계 회고
Accrual·Ledger·Wallet으로 회계 경계를 나눈 이유금전성 상태와 불변 조건을 분리한 모델링 회고

03 · Point Lifecycle

포인트 사용·환불·만료를 Lot 단위로 추적했습니다

사용자 잔액 하나만 감소시키면 어떤 적립분을 사용했는지 알 수 없어 환불과 만료 정책을 정확히 복원할 수 없습니다.

  1. 01

    사용

    지갑을 잠그고 멱등키를 확인한 뒤, 만료일 오름차순·동일 만료일 생성 순서로 Lot을 배분해 차감합니다.

  2. 02

    사용 내역

    LedgerLotSpend에 원결제 Ledger와 실제 차감 Lot·수량의 연결을 남깁니다.

  3. 03

    환불

    원결제에서 사용한 Lot 내역을 기준으로 CREDIT Ledger와 환불 Lot을 만들고 중복 복원을 차단합니다.

  4. 04

    만료

    만료된 잔량은 청크 단위로 소각하고 EXPIRE 원장을 남겨 지갑 잔액과 이력을 함께 맞춥니다.

04 · Referral & Policy

추천 관계, 계보 조회, 보상 산정을 분리해 모델링했습니다

포인트 보상은 단순 지급 기능이 아니라 결제 이벤트, 추천 관계, 추천 계보, 티어 정책, 확정·만료 시점이 함께 맞물리는 도메인이었습니다. 직접 추천 관계와 전체 계보, 보상 산정과 회계 반영을 서로 다른 변경 이유로 나눴습니다.

  • 같은 결제 이벤트에서 구매자 보상과 추천인 보상을 분리해 각각 다른 수령자·정책·멱등키로 처리했습니다.
  • 주문 실결제액과 통화별 환율을 기준으로 포인트를 계산하고, effective tier에 맞는 RewardPayoutRule을 적용했습니다.
  • confirmDay와 expireAfterDays 정책으로 지급 확정 시점과 만료 시점을 분리했습니다.
  • 추천 관계가 없거나 정책·금액 조건이 맞지 않는 경우는 실패가 아니라 명시적인 skip reason으로 남겼습니다.
  • Referral에는 직접 추천 관계를, ReferralClosure에는 self/direct/ancestor 계보를 남겨 보상 판단과 하위 라인 조회를 분리했습니다.
  • 추천 정책은 보상 대상과 금액을 산정하고, 실제 잔액 반영은 Accrual·Ledger·Wallet 회계 흐름에 위임했습니다.
  • 자기 추천, 중복 추천인 등록, 하위 추천인이 있는 사용자의 상위 추천 변경은 차단 조건으로 뒀습니다.
관련 설계 회고
Closure Table과 적립 원장을 함께 사용한 이유추천 계층 탐색과 보상 발생 이력을 분리한 설계 회고

05 · Tier & Policy

티어를 보상률·쿼터·자동 승급의 운영 기준으로 분리했습니다

티어는 단순 표시 등급이 아니라 보상률, 게시글·댓글 쿼터, 자동 승급, 관리자 override가 함께 참조하는 정책 기준이었습니다. 그래서 사용자 프로필의 현재 등급, 운영자 override, 변경 이력을 분리했습니다.

  • 보상 계산은 화면 등급이 아니라 effective tier를 기준으로 수행했습니다.
  • 자동 승급이 관리자가 지정한 overrideTier를 덮어쓰지 않도록 tierId와 overrideTierId를 분리했습니다.
  • 게시글·댓글 쿼터와 결제액 기반 승급 조건은 PolicyRule로 관리해 코드 하드코딩을 줄였습니다.
  • UserTierHistory로 등급 변경의 시작·종료 시점을 남겨 운영자가 변경 이력을 추적할 수 있게 했습니다.

06 · Community Reward Input

커뮤니티 활동을 보상·알림의 입력 이벤트로 해석했습니다

게시글·댓글·좋아요는 커뮤니티 기능인 동시에 보상과 알림을 발생시키는 사용자 행동입니다. 커뮤니티 도메인은 콘텐츠 상태를 책임지고, 보상·알림은 Outbox 이벤트 이후 별도 경계에서 처리되도록 나눴습니다.

  • 게시글·댓글 생성은 커뮤니티 도메인의 결과이면서 보상 도메인의 입력 이벤트가 됩니다.
  • 게시글·댓글 삭제는 이미 발생한 보상 중 취소 가능한 Accrual을 찾아 취소하는 별도 흐름으로 해석했습니다.
  • 댓글·좋아요 마일스톤 알림은 커뮤니티 활동의 사용자 피드백으로 두되, 알림 전송 실패가 게시글 작성 결과를 되돌리지 않게 했습니다.
  • 게시글 쿼터는 hard fail보다 보상 미지급 기준으로 두어 사용자 활동과 보상 정책을 분리했습니다.

07 · Invariants

포인트 모델은 잔액보다 변경 근거를 먼저 보존합니다

전문가가 가장 먼저 확인할 지점은 “어떤 테이블이 있는가”보다 “어떤 조건이 깨지면 안 되는가”입니다. 공개 페이지에는 내부 컬럼 전체가 아니라 운영 중 방어해야 하는 불변 조건을 남겼습니다.

  • Wallet 잔액은 Ledger 없이 직접 증가하지 않습니다.
  • 같은 이벤트·배치·멱등키는 같은 회계 결과로 수렴해야 합니다.
  • Ledger는 append-only 변경 근거이며, 환불·취소는 새 보정 기록으로 설명합니다.
  • 포인트 사용은 Lot의 출처·잔량·만료일을 기준으로 연결되고, 환불은 실제 사용한 Lot을 기준으로 복원합니다.
  • 알림 실패와 FCM 장애는 Ledger·Wallet 트랜잭션 결과를 되돌리지 않습니다.
공개 범위

회사 내부 스키마와 실제 운영 식별자는 공개하지 않고, 모델 책임·상태 전이·불변 조건·복구 기준만 공개 가능한 수준으로 재작성했습니다.

08 · Architecture

도메인, 회계, 이벤트 전달, 알림 전송의 책임을 분리했습니다

동일한 요청 안에서 반드시 함께 확정되어야 하는 상태는 PostgreSQL 트랜잭션으로 묶고, 외부 시스템과 후속 처리는 재시도 가능한 비동기 경로로 분리했습니다.

09 · Payment & Event Delivery

결제 확정, 보상 이벤트, 알림 전달의 실패 경계를 분리했습니다

알림은 단순 FCM 호출이 아니라 사용자에게 남길 인앱 기록, 기기 푸시, 재시도 상태, 중복 방지 기준이 함께 필요한 도메인이었습니다. 그래서 결제·보상 트랜잭션과 알림 전달 상태를 분리하고, 채널별 전송 정책을 별도 경계로 뒀습니다.

  • 카드는 승인 시점, 가상계좌는 입금 확인 시점을 기준으로 내부 결제 상태를 확정했습니다.
  • 인앱 저장 알림과 FCM 푸시는 실패 특성이 달라 채널 정책과 전송 어댑터를 분리했습니다.
  • 포인트 적립, 환불, 추천 가입, 수강 완료, 댓글·좋아요 알림은 타입별 메시지 생성 규칙만 확장하도록 뒀습니다.

Transactional Outbox

선택

도메인 데이터와 Outbox 레코드를 같은 DB 트랜잭션에서 저장한 뒤 BullMQ로 전달했습니다.

문제
결제·게시글은 저장됐지만 보상 이벤트 발행이 실패하면 누락이 발생합니다.
이유
최소 한 번 처리와 재시도를 확보하고, Consumer의 멱등성으로 중복을 흡수합니다.
방어 장치
  • jobId dedup
  • Outbox dedupKey
  • 스테일 복구
  • DEAD 상태

알림 전달 상태와 큐 분리

선택

도메인 OUTBOX 큐와 NOTIFICATION 큐를 분리하고, NotificationDelivery를 PENDING/ENQUEUED/SENDING/FAILED/DEAD 상태로 추적했습니다.

문제
FCM 장애나 대량 알림이 결제·보상 이벤트 처리를 지연시키면 안 됩니다.
이유
금전성 처리와 사용자 메시지의 재시도·장애 정책을 독립적으로 운영할 수 있고, 멈춘 지점을 상태 기준으로 복구할 수 있습니다.
방어 장치
  • stale ENQUEUED 복구
  • stale SENDING 복구
  • jobId 기반 중복 방지
  • FAILED/DEAD 재처리 기준
관련 설계 회고

10 · Application Flow

Facade 계층으로 이벤트별 보상 흐름을 한곳에서 읽히게 만들었습니다

게시글·댓글·가입·결제·추천 이벤트마다 필요한 조회와 정책이 달랐습니다. RewardsFacade가 흐름을 조립하고, RewardsService는 정책 조회와 금액 계산, AccrualsService는 회계 기록을 담당하도록 경계를 나눴습니다.

  • Outbox 핸들러가 모든 조회와 정책 계산을 직접 들고 있지 않게 RewardsFacade가 실행 순서를 모았습니다.
  • RewardsService는 정책·수령자·금액 계산을 맡고, Accrual·Ledger 계층은 실제 회계 반영을 담당했습니다.
  • 보상 결과는 회계 흐름으로 확정하고, 알림은 Outbox 이후 별도 Notification 경로에서 재시도했습니다.
  • 명시적인 skip reason, 이벤트별 독립 멱등키, 영구 오류와 재시도 오류 구분으로 운영 디버깅 기준을 남겼습니다.

11 · Infrastructure & Operations

단일 EC2·공용 ALB에서 전용 ALB·ASG 운영 구조로 전환했습니다

기존 구조는 공용 ALB의 Host Header 분기와 단일 EC2, SSH 기반 배포 흐름에 묶여 있었습니다. 이를 서비스 전용 ALB, Target Group, Auto Scaling Group, GitHub Actions·S3·CodeDeploy 배포 구조로 전환하며 인스턴스 교체·배포 검증·복구 판단 기준을 분리했습니다.

전환 과정

공용 ALB·단일 EC2 → CodeDeploy → 전용 ALB·ASG

먼저 SSH 배포 흐름을 CodeDeploy 배포 파이프라인으로 옮기고, 이후 서비스 전용 ALB와 ASG 기준으로 실행·교체·검증 단위를 정리했습니다.

단계를 선택하면 오른쪽 설명과 아래 인프라 구조가 함께 바뀝니다.

시작점

공용 ALB·단일 EC2·SSH 배포

전환 전에는 공용 ALB에서 Host Header로 서비스를 나누고, 단일 EC2에 SSH 기반으로 배포하는 흐름이 남아 있었습니다.

  • 공용 ALB Host Header 룰에 여러 서비스가 함께 묶여 서비스 간 결합도가 높음
  • 단일 EC2 장애 시 자동 교체가 되지 않아 수동 복구가 필요
  • SSH 배포 흐름이 남아 있어 배포 대상과 실행 결과 추적이 제한적
  • 인스턴스 내부 직접 변경은 교체 시 소실될 수 있어 변경 기준 정리가 필요
관련 설계 회고
단일 EC2·SSH 배포를 ASG·CodeDeploy 검증 경로로 전환한 과정기존 경로를 유지하며 배포·교체·복구 경계를 점진적으로 옮긴 회고

12 · Reliability

정산 재실행과 동시 처리를 안전하게 만들었습니다

월 1,400만+ 포인트 규모의 배치는 잔액을 한 번에 더하는 문제가 아니라, 지급 예정 기록을 선점하고 Ledger·Lot·Wallet을 같은 트랜잭션에서 맞춘 뒤, 실패·중단·만료가 다시 실행돼도 같은 결과로 수렴하게 만드는 문제였습니다.

  1. 01

    Accrual

    보상 이벤트를 지급 예정 기록으로 저장하고, availableAt과 expiresAt으로 확정 시점과 만료 기준을 분리합니다.

  2. 02

    Settlement Batch

    확정 가능한 PENDING Accrual을 제한된 크기로 선점하고, 개별 실패가 전체 회차를 막지 않게 처리합니다.

  3. 03

    Ledger + Lot

    확정 결과는 수정하지 않는 Ledger로 남기고, Lot에는 출처·잔량·만료일을 남겨 사용·환불·만료를 추적합니다.

  4. 04

    Wallet

    사용자 조회용 현재 잔액은 Ledger 포스팅과 같은 트랜잭션에서 갱신하고, Lot 잔량 합계와 맞는지 검증합니다.

작업 선점과 프로세스 중복 방지

선택

PENDING 상태인 행만 PROCESSING으로 바꾸는 조건부 update를 선점 단계로 사용했습니다.

문제
여러 실행 주체가 같은 Accrual을 처리하면 이중 지급이 발생할 수 있습니다.
이유
이미 다른 실행이 선점한 건은 update count가 0이 되어 즉시 건너뜁니다.
방어 장치
  • 한 회차 완료 후 다음 실행을 예약하는 self-rescheduling
  • 스테일 PROCESSING 복구

잔액 동시성 제어

선택

지갑 행을 SELECT FOR UPDATE로 잠근 뒤 최신 잔액을 기준으로 Ledger와 Wallet을 함께 갱신했습니다.

문제
적립·사용·환불이 동시에 같은 지갑을 수정하면 lost update가 발생할 수 있습니다.
이유
동일 사용자·자산의 잔액 변경을 직렬화하면서 다른 지갑의 처리는 병렬로 유지합니다.

재실행 멱등성

선택

walletId + idempotencyKey 유일성 제약과 기존 Ledger 재사용 경로를 두었습니다.

문제
트랜잭션 결과를 응답받기 전에 프로세스가 중단되면 같은 정산이 다시 실행될 수 있습니다.
이유
이미 원장 반영이 끝난 건은 잔액을 다시 증가시키지 않고 Accrual 상태만 POSTED로 복구합니다.
방어 장치
  • FAILED 쿨다운 후 재시도
  • 개별 실패 격리
  • 처리 결과별 운영 로그
운영 기준

정산 루프는 5초 단위로 재스케줄링하고, 회차당 50개 단위로 처리했습니다. PROCESSING에 멈춘 항목은 10분 후 복구하고, FAILED 항목은 1분 쿨다운 후 재시도하도록 분리했습니다.

관련 설계 회고
실패한 포인트 정산을 멱등하게 되돌리는 자기 재스케줄링 배치중첩 실행 방지, 상태 선점, stale 작업 복구 기준을 정리한 상세 회고

13 · Operations Evidence

운영 가능성은 상태·로그·runbook 기준으로 검증했습니다

운영 가능하다는 주장은 패턴 이름만으로 충분하지 않습니다. 어떤 도메인 상태와 정책 수치를 보고, 어떤 범위만 재처리하고, 어떤 수치는 공개 가능한지 구분했습니다.

  • Outbox와 NotificationDelivery는 PENDING, ENQUEUED, SENDING, FAILED, DEAD 같은 상태로 멈춘 지점을 드러냅니다.
  • DEAD 레코드는 전체 재처리가 아니라 타입·원인별로 재처리해야 하며, 운영자 판단이 필요한 상태로 분리했습니다.
  • queue backlog, stale 상태, provider 장애는 도메인 트랜잭션 실패와 같은 의미로 보지 않고 별도 진단 기준을 둡니다.
  • ALB/ASG/CodeDeploy/CloudWatch 기준의 헬스체크·로그 수집·배포 경계를 문서화했습니다.
  • 현재 접근할 수 없는 운영 p95, 오류율, uptime은 임의 성과 수치로 쓰지 않고, 설계·코드·운영 기록으로 확인 가능한 범위만 표기합니다.
  1. 01

    정책·처리 수치

    정산 루프 5초, chunk 50개, stale 10분, 실패 재시도 1분은 처리량 자랑이 아니라 재처리 기준을 고정한 운영 수치입니다.

  2. 02

    상태 기록

    Accrual, Ledger, Wallet, Outbox, NotificationDelivery 상태를 기준으로 어떤 작업이 확정됐고 어디서 멈췄는지 판단합니다.

  3. 03

    복구 단위

    DEAD, FAILED, stale 상태는 전체 재실행이 아니라 타입·원인·idempotency key별 재처리 대상으로 분리합니다.

  4. 04

    미보유 지표

    운영 p95, 오류율, uptime, 정확 처리량은 현재 검증 가능한 원본 로그가 없어 성과 수치로 사용하지 않습니다.

동기 요청과 재처리 작업의 경계

선택

API 서버는 주문·결제·원장 상태를 확정하고, 배치와 BullMQ worker는 Accrual 정산, Outbox 발행, NotificationDelivery 재시도를 담당하도록 나눴습니다.

문제
사용자 결제와 잔액 조회는 즉시 응답해야 하지만, 보상 정산·알림 전송·실패 복구는 같은 요청 안에서 끝낼 필요가 없습니다.
이유
사용자 요청의 지연을 줄이면서도 실패한 후속 처리는 DB 상태를 기준으로 다시 실행할 수 있습니다.
방어 장치
  • PENDING/PROCESSING/FAILED/DEAD 상태
  • Outbox dedupKey
  • worker 재시도
  • 운영 runbook

관측과 복구 기준

선택

CloudWatch 로그, DB 상태, 큐 backlog, DEAD 레코드, stale ENQUEUED/SENDING 복구 기준을 분리해 운영자가 멈춘 지점을 확인할 수 있게 했습니다.

문제
ElastiCache Redis, BullMQ, FCM, PG처럼 실패 특성이 다른 외부 시스템을 한 트랜잭션이나 한 재시도 정책에 묶으면 장애 원인과 복구 경로가 흐려집니다.
이유
운영 가능한 구조는 장애가 없다는 뜻이 아니라, 장애 이후 어떤 상태를 보고 무엇을 재실행할지 설명할 수 있는 구조입니다.
방어 장치
  • CloudWatch 로그 키워드
  • 타입별 DEAD 재처리
  • 전체 DEAD 일괄 복구 금지
  • 큐별 backlog 확인

14 · Outcome & Review

운영 가능한 정합성 구조를 만들었고, 남은 위험도 명시적으로 남겼습니다

  • 적립 예정부터 정산·사용·환불·만료까지 이어지는 포인트 흐름을 운영했고, 복구 기준은 상태·로그·runbook으로 분리했습니다.
  • 적립·사용·환불·만료의 원인과 변경 이력을 Ledger와 Lot으로 추적할 수 있게 했습니다.
  • 재실행·중복 이벤트·동시 잔액 변경에 대한 방어가 서비스 코드와 DB 제약에 함께 존재합니다.
  • 도메인 이벤트와 알림 장애를 분리해 금전성 처리의 실패 범위를 줄였습니다.
정직한 범위 표시

운영 처리량과 금액 규모는 현재 검증 가능한 원본 로그가 없어 성과 수치로 사용하지 않습니다. 대신 코드에서 확인되는 상태·불변 조건·복구 경계를 공개합니다.

Outcome

확인 가능한 결과

  • 적립 예정·정산·사용·환불·만료를 잇는 포인트 회계 파이프라인 운영
  • 조건부 선점·Wallet 행 잠금·Ledger 멱등키로 중복 지급과 잔액 불일치 방어
  • 원거래 Lot 기반 포인트 사용·환불·만료 추적
  • 정책 기반 티어·추천 보상과 Outbox·알림 파이프라인 연결

Limitations

한계와 미구현 범위

  • 정확한 월 처리 레코드 수·TPS·P95 지표는 보존된 운영 자료로 검증하지 못해 공개하지 않습니다.
  • 일부 취소 API의 상태 검증은 조건부 update로 더 원자적으로 개선할 여지가 있습니다.
  • 알림 전달 등급별 retry 정책과 WebSocket 채널은 후속 확장 범위입니다.
Confidentiality

회사명·서비스명·내부 API·테이블 식별자는 공개하지 않고, 구조와 의사결정을 일반화했습니다.
