Constraints

먼저 해결해야 했던 제약

  • 보상 발생, 정산, 사용, 환불, 만료 시점이 달라 같은 잔액 필드로 처리할 수 없었습니다.
  • 같은 이벤트나 정산 배치가 반복 실행돼도 포인트가 한 번만 반영되어야 했습니다.
  • 적립·사용·환불이 동시에 발생해도 사용자 잔액과 원장 기록이 어긋나면 안 됐습니다.
  • 운영 정책, 언어, 국가, 통화, 법적 권역은 서로 다른 속도로 바뀔 수 있었습니다.
  • 결제나 알림 같은 외부 연동 실패가 확정된 금전성 결과를 되돌리면 안 됐습니다.

Project Overview

영상 강의 커머스와 커뮤니티 참여를 보상·결제·운영 정책으로 연결한 교육 플랫폼입니다

기존에 분산되어 운영되던 영상, 리뷰, 회원 데이터를 한 서비스로 통합하고, 강의 구매·커뮤니티 활동·추천 유입을 재방문과 구매로 이어지는 흐름으로 묶었습니다.

  • 사용자 흐름은 강의 탐색·구매, 포인트 적립·사용, 등급 성장, 추천 보상, 커뮤니티 참여가 서로 연결되는 구조였습니다.
  • 운영 정책은 보상률, 티어 조건, 추천 관계, 표시 언어, 약관, 알림, 결제 통화가 서로 다른 속도로 바뀔 수 있었습니다.
  • 그래서 보상 발생·정산·사용·환불·만료 시점을 한 필드로 뭉치지 않고 지급 예정, 불변 원장, 잔액, 주문, 결제, 환불 상태로 분리했습니다.
  • 외부 결제와 알림 전송은 실패할 수 있다는 전제로 트랜잭션, 멱등성, Outbox, 큐 재처리 경계를 두었습니다.

Project Implementation Roadmap

영상 강의와 커뮤니티 요구가 결제·보상·운영 구조로 확장된 순서입니다

강의 구매와 커뮤니티 참여가 만든 요구를 커밋 이력과 문서 기준으로 Phase별로 정리했습니다.

  1. 01

    Phase 01 · 강의 상품과 수강권 · 2025.10–2025.11 · 2개월

    제품·강의·챕터·가격·수강권을 먼저 정리하고 언어별 상품·카테고리 표시 기준을 붙여 사용자가 어떤 콘텐츠를 구매하고 접근 권한을 얻는지 고정했습니다.

  2. 02

    Phase 02 · 커뮤니티 활동 · 2025.10–2026.04 · 7개월

    게시글·댓글·신고·랭킹을 확장하며 커뮤니티 활동을 독립 기능이자 이후 보상·알림의 입력 이벤트로 다룰 수 있게 했습니다.

  3. 03

    Phase 03 · 결제와 환불 경계 · 2025.11–2026.04 · 6개월

    주문, 결제 승인, 가상계좌, 무료 주문, 환불 제한, 국내·해외 PG와 통화 기준을 분리해 구매 결과와 수강권 상태가 같은 기준으로 정리되게 했습니다.

  4. 04

    Phase 04 · 포인트 회계와 정산 · 2026.02–2026.04 · 3개월

    활동·구매 보상을 즉시 잔액으로 더하지 않고 Accrual, Ledger, Lot, Wallet로 나눠 지급 예정·확정·사용·환불을 추적했습니다.

  5. 05

    Phase 05 · 추천·티어·정책 · 2026.02–2026.04 · 3개월

    추천 관계, 추천 계보, 티어 이력, 보상 정책을 별도 모델로 분리해 운영자가 바꾸는 규칙과 사용자의 상태 이력을 구분했습니다.

  6. 06

    Phase 06 · 이벤트·알림 · 2026.04–2026.05 · 2개월

    Outbox, BullMQ, NotificationDelivery, 언어별 알림 메시지, 배포·인프라 경계를 붙여 실패 재처리와 운영 확인이 가능한 구조로 확장했습니다.

상세 작성 기준

Phase 01 · 강의·수강권

강의·수강권

Phase 01

영상 강의는 상품·챕터·카테고리·언어·접근 권한으로 나눠 모델링했습니다

초기 강의 요구는 상품 등록과 구매에 가까웠지만, 실제 서비스에서는 강의 구조, 표시 언어, 분류, 가격, 수강권이 서로 다른 책임으로 관리되어야 했습니다.

  1. 01

    요구 분석

    강의 탐색, 언어별 상품 노출, 카테고리 필터, 챕터 구성, 무료 미리보기, 구매 후 시청, 진행 상태, 환불 제한 시점을 하나의 사용자 여정으로 묶었습니다.

    • 사용자 질문은 “무엇을 살 수 있는가”보다 “구매 후 어디까지 볼 수 있는가”에 가까웠습니다.
    • 상품명·부제·소개는 상품 언어에 따라 달라지고, 카테고리는 같은 코드를 유지한 채 사용자 언어에 맞는 표시명만 바뀌어야 했습니다.
    • 강의 콘텐츠는 상품 하나로 끝나지 않고 섹션, 챕터, Vimeo 미디어, 무료 미리보기 여부까지 함께 설명되어야 했습니다.
    • 무료 미리보기, 진행 상태, 환불 제한은 상품 정보가 아니라 접근 권한의 상태로 이어졌습니다.
  2. 02

    도메인 모델링

    Product는 판매 상품, LectureProduct는 강의 메타, LectureSection · LectureChapter · LectureMedia는 영상 구조, CategoryTranslation은 분류 표시명을 맡게 했습니다.

    • Product는 언어, 상품명, 부제, 설명, 가격 캐시를 가진 판매·노출 헤더이고, LectureProduct는 개요, 강의 구성 설명, 접근 가능 기간을 가진 강의 확장 모델입니다.
    • LectureProductCategory는 강의와 카탈로그 카테고리를 N:M으로 연결하고, Category 코드는 필터·운영 정본, CategoryTranslation은 언어별 표시명을 담당합니다.
    • LectureChapter는 정렬, 무료 미리보기, 챕터 타입을 보존하고, LectureMedia는 외부 영상 식별자, 재생 시간, 업로드 상태를 보존합니다.
    • ProductPrice는 가격·통화 기준을, Entitlement와 LectureChapterProgress는 구매 후 접근 가능 여부와 시청 진행을 맡도록 분리했습니다.
    • LectureChapterProgress는 수강 이력과 완료 판단을 맡아 결제 상태와 직접 섞이지 않게 했습니다.
  3. 03

    아키텍처 결정

    카탈로그 조회는 사용자 언어 기준으로 상품 언어와 카테고리 번역을 고르고, 구매·접근 권한은 결제 확정 뒤 수강권으로 연결했습니다.

    • 목록 조회는 상품 언어, 활성 상태, 카테고리 코드, 검색어, 가격 필터를 조합해 판매 가능한 강의만 보여줍니다.
    • 응답 조립은 CategoryTranslation에서 현재 언어의 표시명을 고르고, 없으면 안정적인 카테고리 코드로 대체합니다.
    • 구매 확정 후에만 Entitlement가 생기게 해 카탈로그 노출과 접근 권한 생성을 분리했습니다.
    • 환불·수료 판단은 상품명이나 화면 상태가 아니라 OrderItem, Entitlement, Progress를 따라가게 했습니다.
  4. 04

    구현·검증

    카탈로그 DTO · Factory에서 언어별 상품·카테고리·챕터·미디어 응답을 조립하고, 결제 완료 후 OrderItem 기준으로 Entitlement가 생성되는지 검증했습니다.

    • DTO · Factory에서 가격, 카테고리 표시명, 챕터 정렬, 무료 미리보기 영상 노출, 전체 재생 시간을 조립하고, 서비스는 조회 조건과 접근 권한 판단에 집중하게 했습니다.
    • 결제 완료, 수강 진행 업데이트, 관리자 수강권 조회 커밋을 기준으로 흐름이 이어지는지 확인했습니다.
  5. 05

    운영·복구

    구매·환불·수강 완료 이슈는 OrderItem, Entitlement, Progress를 기준으로 어떤 권한이 언제 생기고 취소됐는지 추적하게 했습니다.

    • 접근 권한 문의는 OrderItem → Entitlement → Progress 순서로 원인을 좁힐 수 있습니다.
    • 환불 제한이나 수강 완료 이슈는 “권한 생성/취소 시점”과 “진행 상태”를 나눠 확인합니다.
Phase 01의 기준

이 단계의 핵심은 강의를 판매 상품으로만 보지 않고, 언어·카테고리·가격·결제·시청·환불·수료 흐름에서 참조할 접근 권한 도메인으로 분리한 점입니다. 근거는 카탈로그·카테고리 번역·수강권 커밋과 수강권 아키텍처 문서 기준으로 정리했습니다.

Project Infrastructure

단일 EC2·공용 ALB에서 전용 ALB·ASG 운영 구조로 전환했습니다

공용 ALB·단일 EC2·SSH 배포를 전용 ALB·ASG·CodeDeploy 구조로 전환하고, 교체·검증·복구 기준을 분리했습니다.

  • Outbox와 NotificationDelivery 상태로 어떤 작업이 확정됐고 어디서 멈췄는지 판단했습니다.
  • DEAD, FAILED, 멈춤 상태는 전체 재실행이 아니라 타입·원인·멱등 기준별 재처리 대상으로 분리했습니다.
  • 큐 백로그, 외부 공급자 장애, FCM 장애는 도메인 트랜잭션 실패와 다른 운영 진단 기준으로 봤습니다.
  • 접근할 수 없는 응답 지연 p95, 오류율, 가동 시간은 성과 수치로 쓰지 않고, 상태·로그·운영 문서 근거만 남겼습니다.
전환 과정

공용 ALB·단일 EC2 → CodeDeploy → 전용 ALB·ASG

먼저 SSH 배포 흐름을 CodeDeploy 배포 파이프라인으로 옮기고, 이후 서비스 전용 ALB와 ASG 기준으로 실행·교체·검증 단위를 정리했습니다.

단계를 선택하면 오른쪽 설명과 아래 인프라 구조가 함께 바뀝니다.

시작점

공용 ALB·단일 EC2·SSH 배포

전환 전에는 공용 ALB에서 Host Header로 서비스를 나누고, 단일 EC2에 SSH 기반으로 배포하는 흐름이 남아 있었습니다.

  • 공용 ALB Host Header 룰에 여러 서비스가 함께 묶여 서비스 간 결합도가 높음
  • 단일 EC2 장애 시 자동 교체가 되지 않아 수동 복구가 필요
  • SSH 배포 흐름이 남아 있어 배포 대상과 실행 결과 추적이 제한적
  • 인스턴스 내부 직접 변경은 교체 시 소실될 수 있어 변경 기준 정리가 필요
관련 설계 회고
단일 EC2·SSH 배포를 ASG·CodeDeploy 검증 경로로 전환한 과정기존 경로를 유지하며 배포·교체·복구 경계를 점진적으로 옮긴 회고

Outcome & Review

운영 가능한 정합성 구조와 남은 위험을 함께 정리했습니다

  • 적립 예정부터 정산·사용·환불·만료까지 이어지는 포인트 흐름을 운영했고, 복구 기준은 상태·로그·운영 문서로 분리했습니다.
  • 적립·사용·환불·만료의 원인과 변경 이력을 Ledger와 Lot으로 추적할 수 있게 했습니다.
  • 재실행·중복 이벤트·동시 잔액 변경에 대한 방어가 서비스 코드와 DB 제약에 함께 존재합니다.
  • 도메인 이벤트와 알림 장애를 분리해 금전성 처리의 실패 범위를 줄였습니다.
정직한 범위 표시

월 포인트 정산 수량은 운영 중 확인한 대략치로 표기하고, 정확한 처리 레코드 수·TPS·P95는 보존된 운영 자료가 없어 성과 수치로 사용하지 않습니다.

Outcome

확인 가능한 결과

  • 적립 예정·정산·사용·환불·만료를 잇는 포인트 회계 파이프라인 운영
  • 조건부 선점·Wallet 행 잠금·Ledger 멱등키로 중복 지급과 잔액 불일치 방어
  • 카테고리·약관·알림·결제 통화가 언어·국가 기준을 공유하도록 모델과 서비스 경계 정리
  • 원거래 Lot 기반 포인트 사용·환불·만료 추적
  • 정책 기반 티어·추천 보상과 Outbox·알림 파이프라인 연결

Limitations

한계와 미구현 범위

  • 정확한 월 처리 레코드 수·TPS·P95 지표는 보존된 운영 자료로 검증하지 못해 공개하지 않습니다.
  • 일부 취소 API의 상태 검증은 조건부 update로 더 원자적으로 개선할 여지가 있습니다.
  • 알림 전달 등급별 retry 정책과 WebSocket 채널은 후속 확장 범위입니다.
  • 멀티 리전 라우팅과 다중 법인 포인트 플랫폼은 구현 완료 범위가 아니라 ADR과 장기 전환 전략으로만 표시합니다.
