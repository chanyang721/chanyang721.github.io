근거 중심 엔지니어링 포트폴리오

빠른 화면 초안에서 시작해 읽기 불편, 근거 거리, 공개 경계를 발견하며 구조를 다듬은 엔지니어링 포트폴리오입니다.

Project Overview

포트폴리오 개편 과정을 공개 가능한 작업 사례로 재구성했습니다

문제는 회사 경험, 문서, 회고, 커밋 이력이 많이 남아 있어도 읽는 사람이 빠르게 판단할 수 있는 순서와 공개 가능한 근거 경계로 정리되어 있지 않다는 점이었습니다.

이 개인 프로젝트는 대표 백엔드 사례처럼 상태·권한·재처리를 먼저 설계한 것이 아니라, 먼저 화면을 만들고 실제 읽기 흐름에서 막히는 지점을 요구사항으로 되돌려 잡은 사례입니다.

기획, 콘텐츠 모델, 프론트엔드 구현을 맡아 대표 프로젝트는 채용 판단용 요약으로, 상세 페이지는 기술 검수용 근거로, 개인 프로젝트는 작업 방식의 공개 예시로 나눴습니다. 모든 고민을 그대로 노출하지 않고, 독자가 판단하는 데 도움이 되는 선택·수정·검증만 남겼습니다.

공개 기준

모든 대화와 수정 내역을 그대로 보여주는 대신, 독자가 판단할 수 있는 문제 제기, 선택 이유, 바꾼 구조, 검증 결과만 남깁니다.

Ownership

직접 담당한 범위

  • 초기에는 빠르게 화면을 만들고, 읽기 불편·중복·근거 부족이 실제로 보이는 지점부터 구조화
  • 대표 프로젝트처럼 모든 사례에 같은 순서를 강제하지 않고, 프로젝트 성격에 따라 먼저 확인해야 할 경계를 다르게 설정
  • 원천 경험을 프로젝트, 주장, 근거, 공개 경계, 한계 단위로 나눠 필요한 시점에 콘텐츠 모델로 승격
  • 대표 프로젝트, 개인 프로젝트, Career/Production evidence, Implementation Timeline이 서로 다른 정보 깊이를 맡도록 IA 재구성
  • PDR, 페르소나 리뷰, 링크 감사, UI·리팩터링 이력, 커밋·작업 검토 기록, 타입 체크, 빌드 검증을 통해 과장 표현과 깨진 앵커를 반복적으로 줄임

Constraints

먼저 해결해야 했던 제약

  • 회사 코드, 실제 서비스명, 내부 URL, API 경로, DB 테이블명, 운영 식별자는 공개하지 않아야 했습니다.
  • 리크루터는 빠르게 강점을 파악하고, 기술 검수자는 필요한 경우 설계 근거까지 내려갈 수 있어야 했습니다.
  • 프로젝트마다 필요한 검증 순서가 달라 하나의 표준 플로우를 강제하는 인상을 피해야 했습니다.
  • 작업 메모·코드·문서·커밋은 내부 검증에 사용하되 공개 화면에는 판단에 필요한 주장·근거·한계만 남겨야 했습니다.
  • 방문·전환 데이터는 아직 없으므로 정성적 페르소나 검토와 링크·빌드 검증까지만 성과로 말해야 했습니다.

Implementation Timeline

빠른 초안, 화면 관찰, 근거 정본화, 선택형 탐색, 회귀 검증 순서로 재구성했습니다

처음부터 완성된 설계를 세운 것이 아니라, 2026.07 말부터 2026.08 초까지 약 2주간 화면을 만들고 걸리는 지점을 발견하며 필요한 구조만 뒤늦게 승격한 흐름을 Phase별로 정리했습니다. 필요한 Phase를 선택하면 해당 단계에서 어떤 문제를 보고 어떤 구조와 검증 기준으로 이어졌는지 확인할 수 있습니다.

Phase 01 · 독자 요구와 포트폴리오 IA

독자 요구와 포트폴리오 IA

Phase 01 · Reader Journey

빠른 화면 초안에서 독자 질문을 역추적했습니다

처음부터 모든 독자 여정을 문서로 확정하지 않고, 홈과 상세 화면을 먼저 만든 뒤 누가 어떤 질문에서 멈추는지 요구사항으로 되돌려 잡았습니다.

  1. 01

    독자 가설

    먼저 “누가 이 사이트를 어떤 시간 안에 볼까”를 가설로 두고, 독자별로 필요한 판단 깊이를 나눴습니다.

    • 리크루터는 포지셔닝·대표 수치·연락 경로를 빠르게 찾는 독자로 정의했습니다.
    • 기술 검수자는 문제·제약·대안·한계·근거 링크를 확인하려는 독자로 정의했습니다.
  2. 02

    빠른 홈 초안

    홈, 대표 프로젝트, 방법론 섹션을 먼저 화면으로 만들고 실제 읽기 순서에서 어색한 지점을 찾았습니다.

    • 초기 구현에서는 일부 중복과 긴 설명을 허용하고, 먼저 전체 흐름이 보이는지 확인했습니다.
    • 만든 뒤 Home, Method, Case Study, Reflection, CTA의 깊이가 서로 다른 역할을 가져야 한다는 문제가 드러났습니다.
  3. 03

    노출 위계 조정

    화면을 본 뒤 대표 프로젝트, 개인 프로젝트, 초기·보조 경험이 같은 무게로 보이는 문제를 조정했습니다.

    • 초기·보조 경험을 홈 카드에서 내리고 상세 라우트와 Career/Production evidence 링크로 보존해 대표성이 높은 사례가 먼저 읽히게 했습니다.
    • 개인 프로젝트는 실서비스 성과가 아니라 “요구를 분석하고 정보를 모델링하는 방식”을 보여주는 보조 사례로 위치를 제한했습니다.
    • 방법론은 별도 설명이 아니라 대표 프로젝트로 들어가는 네비게이션 역할을 하도록 정리했습니다.
  4. 04

    피드백 기반 수정

    페르소나 리뷰와 PDR을 기준으로 “너무 길다”, “근거가 멀다”, “대표성이 흐려진다”는 문제를 수정 기준으로 삼았습니다.

    • PDR-002, PDR-004, PDR-005, PDR-008에서 대표 프로젝트 축소, 3단계 정보 깊이, 필터 제거, 추가 경험 비노출 전환을 기록했습니다.
    • PDR-009에서는 홈·상세·프로세스 UI 변화와 리팩터링 이유를 커밋 및 작업 검토 기록으로 다시 대조했습니다.
    • 프로젝트 상세가 검증 문서처럼 길어지는 문제는 Implementation Timeline 선택형 구조로 완화했습니다.
  5. 05

    측정 보류

    아직 방문·전환 지표는 없으므로, 현재는 화면 검토와 CTA/PDF 미구현 상태를 한계로 남겼습니다.

    • PDR-007은 채용 전환 CTA와 PDF 역할 분리를 proposed 상태로 유지해 완료 범위를 과장하지 않았습니다.
    • 배포 후에는 프로젝트별 클릭, 회고 링크 이동, 이메일 전환을 다음 검증 대상으로 둡니다.

대표 경험과 경력 연속성의 위계 분리

선택

최근 핵심 사례는 대표 프로젝트로 유지하고, 초기·보조 경험은 홈 카드가 아니라 Career와 근거 링크에서 확인하게 했습니다.

문제
모든 회사 프로젝트를 같은 크기로 보여주면 대표성이 높은 사례의 비중이 희석됐습니다.
이유
첫 방문자는 대표성이 높은 사례와 작업 방식만 빠르게 보고, 필요할 때 경력 연속성을 별도 경로에서 확인할 수 있습니다.

Trade-off초기 프로젝트의 홈 노출량은 더 줄었지만, 대표 프로젝트 3개의 선별 기준과 개인 프로젝트의 역할은 더 명확해졌습니다.

Project Infrastructure

콘텐츠 정본, 공개 경로, 검증 경계로 포트폴리오를 운영합니다

포트폴리오 내용이 늘어나도 같은 사실이 어긋나지 않고, 공개 링크와 화면이 깨지지 않도록 세 가지 운영 경계로 나눴습니다.

01콘텐츠 정본
프로젝트 경험요약·상세·한계는 같은 콘텐츠 정본에서 렌더링
방법론 연결방법론 카드와 프로젝트 앵커는 같은 근거 구조를 참조
판단 기록PDR과 Resource Index로 의사결정·원천 자료 추적
↓
02공개 경로
역할별 페이지홈, 프로젝트 상세, 프로세스 페이지를 읽는 깊이별로 분리
검색·공유 기준공개 가능한 페이지 기준으로 메타데이터와 검색 경계를 생성
비공개 정보 제외공개하지 않을 정보는 사이트 문구와 링크에서 제거
↓
03검증 경계

링크 감사내부 앵커와 상세 이동 회귀 확인
빌드 검증정적 페이지 생성과 렌더링 문제 확인
배포 근거의 성격

이 프로젝트에서 배포·인프라 근거는 트래픽 규모가 아니라, 공개 콘텐츠와 링크 계약을 깨지 않게 관리하는 방식입니다.

Outcome

확인 가능한 결과

  • 포트폴리오 개편 과정을 빠른 초안, 화면 관찰, 근거 감사, 선택형 탐색, 회귀 검증으로 설명 가능한 공개 사례로 정리
  • 백엔드 경험을 홈 요약, 방법론, 프로젝트 상세, 회고 근거의 단계적 정보 구조로 변환
  • 6개 프로젝트 상세를 같은 CaseStudy 스키마와 Implementation Timeline 포맷으로 정규화
  • 홈에서는 대표 프로젝트 3개와 개인 프로젝트만 노출하고, 초기·보조 경험은 Career와 근거 링크로 보존
  • PDR, RESOURCE_INDEX, UI·리팩터링·UX 감사 문서를 통해 의사결정 이력과 원천 리소스 탐색 경로를 분리
  • Portfolio Flow와 Implementation Timeline의 역할을 분리해 공통 질문과 프로젝트 내부 근거 사이의 이동 경로를 단축
  • 공개 불가 정보, 근거 부족 수치, 미구현 CTA/PDF 범위를 한계로 명시

Limitations

한계와 미구현 범위

  • 초기 버전은 한국어 단일 언어이며 영문 요약과 PDF 산출물은 후속 범위입니다.
  • 방문, 회고 클릭, 이메일 전환 지표는 아직 수집하지 않아 정성적 페르소나 검토와 링크 감사만 근거로 사용합니다.
  • 회사 코드 저장소와 내부 작업 메모는 비공개로 유지하며 사이트에는 일반화한 증거만 제공합니다.
  • 작업 검토 기록은 UI·리팩터링 판단의 출처로 사용하되, 공개 페이지에는 원문이 아니라 판단과 검증 결과만 남깁니다.
  • CTA/PDF 역할 분리는 PDR-007 proposed 상태로 남아 있어 구현 완료로 표기하지 않습니다.
