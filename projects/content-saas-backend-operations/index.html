Ownership

직접 담당한 범위

  • 위치기반 AR 선물 수령 커머스의 상점·상품·사진·선물·사용자 문서 모델 설계
  • 상점 지오펜스, QR, 예약 수령, 수령·확정·소비 상태를 분리한 선물 생명주기 모델링
  • AR·실물·티켓·이벤트 상품을 단일 상품 흐름과 리소스 타입으로 통합
  • Go/Gin 메인 서버의 부트스트랩·라우터 경계와 NestJS 재구현 라인의 계층 구조 정리
  • Firebase 인증, MongoDB, TypeORM · Mongoose, AWS 어댑터 스캐폴드의 외부 인프라 경계 보존

Constraints

먼저 해결해야 했던 제약

  • 선물은 온라인 결제 객체이면서 특정 물리 위치에서만 수령되는 오프라인 상태를 함께 가져야 했습니다.
  • 수신자가 미리 정해지지 않은 선물도 허용해야 했고, 좌표에 도착한 사람이 획득하는 흐름을 표현해야 했습니다.
  • 상품은 AR 리소스, 실물, 티켓, 이벤트처럼 표현 방식이 달라도 목록·선물 흐름은 하나로 유지해야 했습니다.
  • 아카이브에서 가장 분명하게 확인되는 근거는 완성 API가 아니라 데이터 모델과 아키텍처 골격이었습니다.
  • 원본 git history는 코드베이스별 단일 스냅샷 수준이라 Phase별 실제 개발 기간을 세밀하게 주장할 수 없습니다.
  • 배포 파이프라인, 서버 토폴로지, 운영 지표는 보존 근거가 없어 성과 수치로 사용할 수 없습니다.

Project Overview

위치, QR, 수령 상태가 결합된 AR 선물 커머스를 데이터 모델로 설명한 프로젝트입니다

수령 장소·QR·진행 상태를 데이터로 설명하는 선물 생명주기를 설계했습니다.

공개 가능한 원천을 다시 확인한 결과, 메인 Go 서버의 문서 모델과 라우터 골격, 이후 NestJS 라인에서 계층·인프라 어댑터를 분리한 흔적이 가장 분명하게 확인됐습니다.

  • 특정 장소에서 QR로 선물을 수령하는 경험을 모델링했습니다.
  • 위치, 상품 타입, 수령 상태, 수신자 확정을 별도 변경 지점으로 나눴습니다.
  • Go/Gin은 도메인 정본, NestJS는 계층·인프라 분리 근거로 범위를 한정했습니다.

Phase 01 · 위치·지오펜스 도메인

위치·지오펜스 도메인

Phase 01

“장소에 도착해야 받을 수 있다”는 요구를 위치 조건으로 분리했습니다

상점의 수령 가능 영역과 선물의 실제 수령 좌표를 별도 책임으로 나눴습니다.

  1. 01

    요구 분석

    선물 수령은 단순 소유권 이전이 아니라 장소, 좌표, 예약 시각이 함께 맞아야 성립하는 경험으로 보았습니다.

    • 상점은 수령 가능한 물리 공간의 기준점이고, 선물은 실제로 놓이거나 수령될 위치를 따로 가져야 했습니다.
    • 수신자가 미리 정해지지 않은 선물도 가능해야 했으므로 “누구에게”보다 “어디에서”가 먼저인 케이스가 있었습니다.
  2. 02

    도메인 모델링

    상점은 중심 좌표와 반경을, 선물은 수령 좌표와 예약 시각을 갖도록 나눴습니다.

    • 상점의 위치 정보는 지오펜스의 기준이고, 선물의 위치 정보는 수령 이벤트의 대상입니다.
    • 좌표는 정밀 수치 타입으로 표현해 위도·경도 값을 문자열이나 부동소수 오차에 느슨하게 맡기지 않았습니다.
  3. 03

    아키텍처 결정

    복잡한 공간 모델보다 원형 지오펜스를 선택해 초기 요구를 단순한 좌표·반경 판단으로 고정했습니다.

    • 폴리곤이나 층 단위 공간은 표현력이 높지만 초기 모델 복잡도가 커집니다.
    • 원형 지오펜스는 한 상점당 하나의 중심과 반경으로 설명 가능해 초기 도메인 검증에 적합했습니다.
  4. 04

    구현·검증

    아카이브된 Go 모델에서 상점 위치·반경, 선물 위치·예약 시각이 별도 문서에 존재하는 것을 확인했습니다.

    • 위치 주변 조회와 좌표 배치 라우터 주석도 같은 도메인 방향을 가리킵니다.
    • 핸들러 구현이 완료되지 않은 구간은 실제 위치 검증 API 성과로 주장하지 않습니다.
  5. 05

    운영·복구

    운영 중 수령 오류를 보면 QR만 확인하지 않고, 상점 지오펜스와 선물 좌표·예약 조건을 함께 확인해야 합니다.

    • 위치 조건이 빠지면 “코드는 맞지만 장소가 아닌 곳에서 받는” 도메인 위반이 생깁니다.
    • 공개 페이지에서는 위치 검증 전략만 설명하고 실제 좌표·상점 정보는 노출하지 않습니다.

    Go/Gin 메인 서버, NestJS 재구현 라인, NestJS 광고 서버가 서로 다른 성숙도와 책임을 가진 snapshot으로 남아 있습니다.

    외부 연동

    Firebase 인증, PASS 인증 전제, AWS 어댑터 스캐폴드가 외부 인프라 경계로 분리되어 있습니다.

    검증 한계

    배포 전략, 서버 토폴로지, 운영 로그, 장애 복구 지표는 현재 원천에서 직접 검증하지 못해 공개 성과로 사용하지 않습니다.

공개 범위

이 섹션은 인프라 “운영 성과”가 아니라 코드에서 확인되는 실행·저장소·외부 연동 경계만 설명합니다.

Outcome

확인 가능한 결과

  • 위치기반 AR 선물 수령 커머스의 위치·QR·상태 중심 도메인 모델 정리
  • 상점, 상품, 사진, 선물, 사용자 모델을 통해 AR 커머스의 핵심 관계를 설명 가능하게 구성
  • AR·실물·티켓·이벤트를 단일 상품 흐름으로 묶는 다형 상품 모델 설계
  • Go/Gin 메인 서버와 NestJS 재구현 라인의 실행·계층·인프라 경계 보존
  • 구현 완료 범위와 스캐폴딩·미확정 범위를 공개 문장에서 분리

Limitations

한계와 미구현 범위

  • 원본 저장소는 코드베이스별 단일 스냅샷 커밋만 확인되어 Phase별 실제 개발 기간을 세밀하게 주장하지 않습니다.
  • 메인 서버 핸들러 구현이 완료되지 않은 구간은 완성 API 운영 성과로 표기하지 않습니다.
  • 일부 enum 값과 리소스 타입 선언에는 아카이브 시점의 미확정·불일치가 있어 한계로 남깁니다.
  • 완성 배포 파이프라인, 서버 토폴로지, 운영 지표는 현재 원천에서 직접 검증 가능한 자료가 없어 상세 주장으로 사용하지 않습니다.
  • 정량 성능 개선, 트래픽, 장애율, 비용 절감 수치는 보존 자료가 없어 공개하지 않습니다.
  • 내부 저장소, 실제 서비스명, 설정·인증 예시, 실제 API 경로는 공개하지 않습니다.
Confidentiality

회사명은 공개 가능한 경력 범위에서 사용하지만, 서비스 식별 정보·내부 API·설정값·인증 예시·운영 지표는 공개하지 않습니다.
