Ownership

직접 담당한 범위

  • 6.7억+ TRANSACTION_HISTORY를 PK 커서와 제한된 검색 범위로 증분 탐색하는 배치 구현
  • StatisticsJob에 게임·컨트랙트별 처리 위치를 저장해 중단 후 재개와 과거 구간 재탐색 지원
  • 게임 트랜잭션 저장과 체크포인트 갱신을 같은 DB 트랜잭션으로 처리
  • Redis 락과 self-rescheduling으로 중복 실행을 방지하면서 신규 데이터 지속 추적
  • ethers.js로 Transfer 이벤트를 파싱하고 tx history, game history, summary로 이어지는 보상 통계 파이프라인 구현
  • Upbit·Binance 가격 수집, 괴리 계산, 전략별 수익률·Sharpe·PnL 백테스트 구현
  • 컨트랙트 신청·심사·승인 워크플로우와 관리 UI 구현

Constraints

먼저 해결해야 했던 제약

  • 원천 트랜잭션은 약 6.7억+ 건 누적되어 전체 스캔이나 OFFSET 방식으로 반복 조회할 수 없었습니다.
  • 신규 데이터가 계속 쌓이는 동안 과거 적체 구간도 따라잡고, 장애 후에는 마지막 처리 위치부터 재개해야 했습니다.
  • 온체인 이벤트는 중복 수집과 누락을 모두 피해야 했습니다.
  • 배치가 중단되거나 재실행돼도 이미 처리한 구간을 안전하게 이어가야 했습니다.
  • 게임별 컨트랙트와 토큰이 추가될 수 있어 동적 job 발견이 필요했습니다.
  • 초 단위로 갱신되는 가격 데이터가 보상 산정과 시각화에 안정적으로 반영되어야 했습니다.
  • 수익률 로깅 도구는 실거래 자동화가 완성되기 전 중단되어, 완성 범위와 미완성 범위를 구분해야 했습니다.
  • 팀 레포 전체가 아니라 공개 가능한 직접 구현 범위만 포트폴리오에 남겨야 했습니다.

Project Overview

온체인 활동을 사용자 보상과 통계로 바꾸는 데이터 파이프라인 프로젝트입니다

사용자는 dApp 활동 결과를 보상 이력과 통계로 확인하고, 운영자는 계속 쌓이는 온체인 트랜잭션에서 승인된 대상과 필요한 구간만 안정적으로 처리해야 했습니다. 이 프로젝트는 단순 배치 최적화가 아니라 신청·심사·승인·수집·변환·요약·복구를 연결한 데이터 백엔드 구축 작업입니다.

  • 서비스 관점에서는 원천 트랜잭션을 사용자에게 의미 있는 보상·통계 데이터로 변환해야 했습니다.
  • 기본 도메인은 컨트랙트 신청, 운영자 심사·승인, 통계 job, 원천 tx history, 게임별 history, 사용자 summary, 보조 파일·메일 인프라로 구성됐습니다.
  • 운영 관점에서는 과거 구간 재탐색, 신규 데이터 추적, 중단 후 재개가 모두 필요했습니다.
  • 확장성과 유지보수성을 위해 승인 대상 발견, 배치 실행, 커서 저장, 결과 집계, 보조 인프라 연동을 서로 다른 변경 지점으로 분리했습니다.
  • 프로젝트의 목적은 대용량 테이블 전체 스캔이 아니라 체크포인트 기반으로 재시작 가능한 처리 흐름을 만드는 것이었습니다.
  1. 01

    요구 분석

    대용량 원천 테이블, 승인된 컨트랙트, 사용자 보상 통계, 운영 재처리 요구를 서로 다른 요구사항 케이스로 분리합니다.

  2. 02

    도메인 모델링

    신청·심사·승인 모델과 StatisticsJob, tx history, game history, summary가 각각 보존할 상태와 확장 지점을 나눕니다.

  3. 03

    아키텍처 결정

    API·어드민·배치를 실행 단위로 분리하고, 승인된 대상 발견과 실제 통계 처리를 독립된 경계로 둡니다.

  4. 04

    구현·검증

    PK 커서, 검색 창, chunk 처리, Transfer 이벤트 파싱, 커서 원자 저장을 코드 기준으로 검증합니다.

  5. 05

    배포·인프라

    Redis lock, self-rescheduling, Azure Blob, mail adapter, Google Drive 적재 경계를 분리합니다.

  6. 06

    운영·복구

    중단 후 재개, 과거 구간 재탐색, 신규 job 발견을 정상 운영 시나리오로 둡니다.

01 · Scale

6.7억+ 원천 데이터를 사용자에게 필요한 보상 통계로 바꿨습니다

운영 당시 TRANSACTION_HISTORY는 약 6.7억+ 건 규모로 누적되어 있었고, 이는 운영 중 직접 확인한 값입니다. 다만 정확한 row count와 처리 시간 로그는 현재 보존되어 있지 않아 대략치로만 표기합니다.

핵심은 테이블 전체를 한 번에 처리한 것이 아니라, 계속 유입되는 신규 데이터와 과거 재탐색 요구를 같은 체크포인트 기반 파이프라인으로 다룬 경험입니다.

  • Primary Key 기준으로 마지막 처리 ID 이후 10,000개 범위만 탐색했습니다.
  • 일치하는 트랜잭션은 최대 50건씩 파싱해 긴 트랜잭션과 메모리 사용을 제한했습니다.
  • StatisticsJob에 컨트랙트별 커서를 저장해 프로세스 중단 후에도 마지막 확정 위치부터 재개했습니다.
  • 결과 저장과 커서 갱신을 같은 DB 트랜잭션으로 묶어 처리되지 않은 구간을 건너뛰지 않도록 했습니다.
  • 처리 완료 후 1초 self-rescheduling으로 최신 데이터를 계속 따라가고, 신규 게임은 별도 발견 루틴으로 편입했습니다.
직접 구현 근거

PK 범위 조회, 10,000 ID 검색 창, 50건 처리 단위, Redis 락, self-rescheduling, 결과·커서 원자적 저장은 chanyang 계정의 코드와 Git 이력에서 확인됩니다.

02 · Measurement Scope

코드로 확인 가능한 지표와 운영 로그가 필요한 지표를 분리했습니다

  • 약 6.7억+는 당시 운영에서 직접 확인한 원천 테이블 규모이며, 정확한 row count 로그는 현재 보존 자료가 없어 대략치로 표기합니다.
  • 1초 self-rescheduling, 10초 job 발견 주기, 10,000 검색 창, 50건 처리 chunk는 직접 작성한 배치 코드에서 확인됩니다.
  • 게임·보상 연결, 통계 배치와 아비트라지 백테스트는 저장소와 작성 자료에서 직접 구현 범위를 확인할 수 있습니다.
  • 초당 처리량, 일 처리량, p95 latency, 오류율은 당시 운영 로그와 모니터링 접근이 필요하므로 현재 포트폴리오 성과 수치로 표기하지 않습니다.
  • 따라서 이 프로젝트는 검증되지 않은 TPS가 아니라 “약 6.7억+ 원천 테이블에서 동작한 커서 기반 탐색과 재시작 가능한 배치 구조”를 증명하는 사례로 배치했습니다.

03 · Contract Approval Model

배치 입력이 되기 전에 컨트랙트 신청·심사·승인 상태를 먼저 모델링했습니다

온체인 배치는 아무 컨트랙트나 읽는 도구가 아니라, dApp이 신청하고 운영자가 검토해 승인한 대상을 보상 통계 입력으로 삼는 플랫폼 흐름 안에 있었습니다.

  • 컨트랙트 신청·심사·승인 워크플로우와 관리 UI는 공개 가능한 직접 구현 범위에 포함됩니다.
  • 첨부 저장은 Azure Blob 경계로 분리해 승인 도메인 상태와 파일 인프라 책임을 섞지 않았습니다.
  • 승인 상태를 배치 입력 조건으로 두어 통계 파이프라인이 임의 컨트랙트까지 확장되지 않게 했습니다.
  • 구체적인 내부 API 경로와 실제 컨트랙트 주소는 공개하지 않습니다.
  1. 01

    Application

    dApp 운영자가 게임·토큰·컨트랙트 정보를 신청하고 심사에 필요한 첨부를 제출합니다.

  2. 02

    Review

    어드민이 신청 내용을 검토하고, 첨부 파일과 운영 메모를 기준으로 승인 여부를 결정합니다.

  3. 03

    Approval

    승인된 컨트랙트만 통계 job 발견 루틴의 대상이 되어 온체인 배치 입력으로 편입됩니다.

  4. 04

    Notification

    승인 결과와 후속 안내는 메일 어댑터 같은 부수효과 경계로 분리합니다.

04 · Reward Statistics Model

온체인 이벤트를 tx history, game history, summary로 단계별 변환했습니다

보상 통계는 원천 트랜잭션을 그대로 노출하는 기능이 아니었습니다. 승인된 게임·토큰 기준으로 필요한 Transfer 이벤트를 찾고, 사용자에게 의미 있는 이력과 요약으로 변환해야 했습니다.

  1. 01

    Approved Source

    승인된 게임·토큰·컨트랙트 정보가 배치의 처리 대상이 됩니다.

  2. 02

    StatisticsJob

    컨트랙트별 처리 커서와 상태를 저장해 어느 구간까지 확정했는지 남깁니다.

  3. 03

    Tx History

    원천 트랜잭션에서 보상 산정에 필요한 이벤트만 파싱하고 처리 단위를 제한합니다.

  4. 04

    Game History

    사용자·게임 기준의 보상 이력으로 변환해 중복 저장과 누락을 방어합니다.

  5. 05

    Summary

    사용자 화면과 운영 조회에 필요한 누적 보상·참여 통계를 집계합니다.

모델링의 핵심

대용량 테이블을 빠르게 읽었다는 주장보다 중요한 것은 “무엇을 원천으로 보고, 어느 지점을 확정 커서로 삼고, 어떤 데이터가 사용자에게 보이는가”를 단계별로 나눴다는 점입니다.

05 · Architecture Boundary

승인 도메인과 통계 배치를 분리해 처리 대상과 실행 책임을 명확히 했습니다

승인된 대상만 배치 입력으로 사용

선택

신청·심사·승인 흐름을 먼저 통과한 컨트랙트를 StatisticsJob 발견 대상에 포함했습니다.

문제
컨트랙트가 계속 추가되는 플랫폼에서는 잘못된 대상이 배치에 들어가면 비용과 데이터 오염이 동시에 발생합니다.
이유
운영자가 검토한 대상과 배치가 처리하는 대상을 같은 상태 기준으로 연결할 수 있습니다.

API·어드민·배치를 독립 실행 단위로 분리

선택

사용자 API, 어드민 승인 흐름, 통계 배치를 별도 실행 책임으로 설명하고 배치에는 커서·락·재시작 기준을 두었습니다.

문제
사용자 조회와 심사 UI, 대용량 인덱싱은 응답 시간과 실패 비용이 다릅니다.
이유
한 실행 경계의 지연이나 실패가 전체 플랫폼 요청-응답 흐름으로 전파되는 것을 줄입니다.

보조 인프라를 도메인 트랜잭션 밖으로 격리

선택

Azure Blob, mail adapter, Google Drive pipeline을 보조 인프라 경계로 분리했습니다.

문제
첨부 저장, 승인 메일, 가격 데이터 적재는 핵심 통계 저장과 실패 특성이 다릅니다.
이유
도메인 상태, 파일 저장, 알림, 연구 데이터 적재의 실패와 재시도 기준을 따로 설명할 수 있습니다.

06 · Pipeline Shape

온체인 트랜잭션을 재시작 가능한 배치 처리 과정으로 나눴습니다

  • 신규 컨트랙트·토큰 발견과 실제 통계 처리를 분리해 운영 중 대상이 추가되어도 배치에 편입되도록 했습니다.
  • StatisticsJob의 JSON data에 lastCheckedTxHistoryId, lastCheckedGameContractTxHistoryId, lastSummarizedGameHistoryId 같은 커서를 남겼습니다.
  • 10,000개 단위로 검색 범위를 전진시키고 50건씩 처리해 긴 트랜잭션과 과도한 메모리 사용을 피했습니다.
  • GameContractTransactionHistory 저장과 StatisticsJob 커서 갱신을 같은 DB 트랜잭션으로 묶어 저장 성공 후 커서만 잃는 상황을 줄였습니다.
  • tx 수집, Transfer 이벤트 파싱, game history 생성, summary 집계를 분리해 실패 지점을 좁혔습니다.
처리량 표현 기준

이 구조만으로 초당 처리량이나 일 처리량을 역산하지 않습니다. 코드에서 확인 가능한 것은 발견 주기, 검색 창, chunk 크기, 커서 갱신 방식이며 실제 throughput은 당시 노드 응답 시간·DB 성능·운영 로그가 있어야 산정할 수 있습니다.

관련 설계 회고
6.7억+ 온체인 트랜잭션을 재시작 가능한 커서 배치로 전환한 회고과거 재탐색과 신규 데이터 추적을 함께 다룬 배치 설계·복구 회고

07 · Batch Runtime

API, 어드민, 통계 배치를 독립 실행 단위로 나눠 온체인 파이프라인을 운영했습니다

POET 플랫폼은 사용자 API, 어드민 승인 흐름, 온체인 통계 배치를 분리된 실행 단위로 두었습니다. 배치는 승인된 컨트랙트와 토큰을 주기적으로 발견하고, Redis 락과 커서 체크포인트를 기준으로 중복 실행 없이 계속 재예약됩니다.

  • 사용자 API와 어드민 승인 흐름, 통계 배치를 한 프로세스 책임으로 설명하지 않고 실행 단위를 분리해 보여줍니다.
  • 승인된 대상만 배치의 입력이 되도록 신청·심사·승인 워크플로우와 통계 job 발견 경계를 나눴습니다.
  • Redis 분산 락과 짧은 TTL로 동일 job 중복 실행을 막고, 완료 후 self-rescheduling으로 다음 처리 사이클을 예약했습니다.
  • StatisticsJob 커서는 배치 재시작 시 전체 재처리 대신 마지막 확정 구간부터 이어가기 위한 운영 상태입니다.
  • 첨부·메일·가격 데이터 적재는 각각 Azure Blob, mail adapter, Google Drive pipeline으로 분리해 주 도메인 트랜잭션과 경계를 나눴습니다.

수치 제한

배치 주기, 검색 창, chunk 크기, 커서·락 구조는 코드로 확인되지만, 당시 인스턴스 스펙·모니터링 로그가 없어서 처리량·가용성 수치는 만들지 않습니다.

08 · Reliability

배치 중단과 재실행을 정상 운영 시나리오로 다뤘습니다

이 프로젝트의 핵심 수치는 성능을 부풀리는 숫자가 아니라, 대용량 원천 데이터를 안전하게 나눠 읽고 다시 이어가기 위해 백엔드가 기록한 제어 기준입니다.

  1. 01

    범위 수치

    약 6.7억+ Row는 운영 당시 확인한 원천 규모이고, 정확 row count 로그가 없어 대략치로만 표기합니다.

  2. 02

    처리 제어 수치

    10,000 검색 창, 50건 chunk, 1초 self-rescheduling은 처리량 성과가 아니라 쿼리 범위·트랜잭션 길이·재예약 기준입니다.

  3. 03

    상태 기록

    StatisticsJob 커서와 상태, Redis lock, 결과 저장 트랜잭션으로 어디까지 확정 처리됐는지 기록합니다.

  4. 04

    미보유 지표

    초당 처리량, 일 처리량, p95, 오류율은 당시 운영 로그가 필요하므로 현재 포트폴리오 성과 수치로 만들지 않습니다.

09 · Arbitrage Research

거래소 가격 괴리를 수집하고 아비트라지 전략을 검증했습니다

  • Upbit·Binance 가격 데이터를 수집하고 거래소 간 가격 괴리를 기준으로 아비트라지 진입·청산 조건을 검증했습니다.
  • 전략별 수익률·Sharpe·누적 PnL을 계산해 단순 가격 비교와 전략 성과 평가를 분리했습니다.
  • USDKRW 환율과 KRW-USDT 캔들 데이터를 시간 단위로 병합해 김치프리미엄 비율을 계산했습니다.
  • 가격 데이터를 1시간 단위로 로컬과 Google Drive에 적재하는 파이프라인을 구성했습니다.
  • 지갑 상태, 전략 상태, 주문 기록, 체결 기록을 kpr_trading_records.xlsx의 별도 시트로 나누어 저장했습니다.
  • 주문 API 응답을 OrderRecord로 변환하고, 체결 가격·수수료·슬리피지·return_ratio·cumulative PnL을 기록할 수 있게 했습니다.
  • 실거래 자동화 노트북은 프로젝트 중단으로 미완성이라, 포트폴리오에서는 가격·수익률 산정/로깅 도구까지를 완료 범위로 표기합니다.

10 · Outcome & Limits

대용량 배치 구조와 직접 구현 범위를 분리해 성과와 한계를 함께 남겼습니다

  • 약 6.7억+ 원천 테이블에서 필요한 구간만 찾는 PK 커서 기반 탐색 구조를 구현했습니다.
  • StatisticsJob 커서, Redis 락, self-rescheduling으로 중단 후 재개 가능한 배치 실행 경계를 만들었습니다.
  • 컨트랙트 신청·심사·승인 워크플로우와 보상 통계 배치의 입력 조건을 연결했습니다.
  • 김치프리미엄 가격 수집·성과 계산·거래 로깅 도구는 연구 파이프라인의 완료 범위로, 실거래 자동화는 미완성으로 분리했습니다.
수치와 소유권의 한계

정확한 row count 로그, 처리량, 인스턴스 스펙, 팀 레포 전체 기여율은 공개 가능한 근거가 부족합니다. 따라서 코드와 Git 이력으로 확인 가능한 커서·락·chunk·저장 흐름만 상세 주장으로 사용합니다.

Outcome

확인 가능한 결과

  • 6.7억+ 원천 트랜잭션을 PK 커서·제한된 검색 범위로 탐색하는 증분 배치 운영
  • 중단 후 재개·과거 구간 재탐색·신규 데이터 지속 추적을 하나의 StatisticsJob 흐름으로 구성
  • 게임 트랜잭션 저장과 처리 커서 갱신을 동일 DB 트랜잭션으로 확정
  • 거래소 가격 괴리 기반 아비트라지 전략의 수익률·Sharpe·누적 PnL 백테스트 구현
  • 온체인 Transfer 이벤트 파싱과 tx history, game history, summary 집계 흐름을 서비스 코드와 테이블로 연결
  • dApp 컨트랙트 등록–심사–승인 워크플로우와 어드민 심사 UI 구현
  • 김치프리미엄 가격 데이터와 거래 결과 로깅 도구 구현

Limitations

한계와 미구현 범위

  • 원천 테이블 규모는 운영 중 직접 확인한 약 6.7억+ 대략치로 표기하며, 정확한 row count와 처리 시간 로그는 보존 자료가 없어 정밀 수치로는 사용하지 않습니다.
  • 코드 구조만으로 TPS·일 처리량을 역산하지 않으며, 실제 처리량은 당시 DB 성능과 데이터 분포에 따라 달라집니다.
  • 공개 웹에는 내부 저장소 구조, API 경로, 파일 단위 기여 수치를 노출하지 않습니다.
  • 팀 레포 전체가 아니라 내가 생성했거나 작성 범위가 확인된 파일 중심의 증거만 사용합니다.
  • KPR 실거래 자동화 노트북은 미완성으로 기록되어 있어, 완성 성과처럼 표현하지 않습니다.
  • 실제 토큰·거래 데이터와 시크릿은 공개하지 않습니다.
Confidentiality

회사명은 이력 공개 범위에서 사용하지만, 내부 저장소·시크릿·실거래 데이터·원본 로그는 공개하지 않습니다.
