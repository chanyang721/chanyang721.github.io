Ownership

직접 담당한 범위

  • 영상 상품과 구독 상품을 공통 Product 헤더와 별도 확장 모델로 분리하고, 영상 길이 기반 접근 정책을 설계
  • 상품·가격·주문·청구서·결제 시도·실결제·구독·빌링키 데이터 모델 설계
  • NICEPAY·Payletter 결제 Adapter, Handler, Processor와 서버 주도 PG 라우팅 구현
  • 구독 최초 결제, 정기 갱신, 실패 재시도, 플랜 변경, 기간말 해지·재개 구현
  • PG 승인 성공 후 내부 확정 실패를 재과금 없이 복구하는 Outbox 경로 설계

Constraints

먼저 해결해야 했던 제약

  • 영상 1개가 서비스의 콘텐츠 단위였으므로 기존 강의/섹션 계층을 그대로 유지하면 상품·구매·시청 권한이 불필요하게 복잡해졌습니다.
  • 구독 상품은 이름이나 티어 문자열이 아니라 “어떤 길이의 영상을 볼 수 있는가”라는 접근 조건으로 설명되어야 했습니다.
  • 접근 조건이 바뀌면 사용자의 구독 row를 일괄 수정하지 않아도 다음 목록·상세·재생 요청부터 권한 판정이 바뀌어야 했습니다.
  • NICEPAY는 동기 빌링키 흐름, Payletter는 결제창·callback 기반 비동기 흐름을 가집니다.
  • 사용자의 최초 구매와 매월 자동 청구를 같은 Order로 관리하면 이력이 왜곡됩니다.
  • 여러 서버가 같은 구독 회차를 동시에 청구해도 PG 과금은 한 번만 발생해야 합니다.
  • PG 승인 성공과 DB 확정 실패가 동시에 발생하는 부분 성공을 복구해야 합니다.
  • 갱신 실패·유예·이용 정지·플랜 변경·해지 정책을 일관된 상태로 관리해야 합니다.

Project Overview

영상 강의 서비스의 요구사항들을 케이스별로 분석해 운영 가능한 도메인 모델로 만든 프로젝트입니다

이 프로젝트는 특정 결제 기능 하나가 아니라 영상 강의 서비스의 판매·청구·권한·복구를 다룬 구축 작업입니다. 먼저 프로젝트 목적과 도메인 구성을 정리한 뒤, 영상 접근, 단건 구매, 최초 구독, 정기 갱신, 플랜 변경·해지 같은 요구사항을 케이스별로 나눠 같은 설계 플로우로 추적했습니다.

  • 사용자 관점에서는 영상 목록, 상세, 구매, 구독 시작, 갱신, 플랜 변경, 기간말 해지가 하나의 서비스 경험으로 보여야 했습니다.
  • 기본 도메인은 영상 카탈로그, 상품·가격, 주문·결제, 구독·청구, 수강권·접근 권한, Outbox·worker, 배포·런타임 경계로 구성됐습니다.
  • 제품 관점에서는 영상 길이에 따른 구독 접근 조건, 단건 구매 수강권, 최초 구독 결제, 반복 청구, 해지 정책이 서로 다른 요구사항 케이스였습니다.
  • 운영 관점에서는 PG별 callback 차이와 부분 성공 상태를 재과금 없이 수렴시켜야 했습니다.
  • 각 케이스는 확장성과 유지보수성을 확인할 수 있도록 정책으로 바뀔 값, 과거 이력으로 고정할 값, 장애 후 복구할 상태를 분리했습니다.
  • 프로젝트의 목적은 PG 연동만이 아니라 여러 요구사항을 영상·구독·구매·청구·결제·권한 모델로 나누고 다시 연결하는 것이었습니다.
  1. 01

    요구 분석

    영상 접근 조건, 단건 구매, 최초 구독 결제, 자동 갱신, 플랜 변경, 해지를 목적·행위·상태 변화가 다른 요구사항 케이스로 분리합니다.

  2. 02

    도메인 모델링

    영상·구독 접근 정책 모델과 Order, Invoice, PaymentIntent, Payment, Entitlement가 각각 답해야 하는 질문을 나눠 변경 이유를 분리합니다.

  3. 03

    아키텍처 결정

    서버 주도 가격·PG 라우팅과 Adapter–Handler–Processor 경계로 외부 PG 차이를 격리해 새 결제 흐름 추가 비용을 낮춥니다.

  4. 04

    구현·검증

    최초 결제, 갱신, callback 순서 역전, 부분 성공 복구를 실제 상태 전이·회귀 테스트·구현 상태 감사로 검증합니다.

  5. 05

    배포·인프라

    동기 결제 API, worker/queue, PostgreSQL, Redis, 외부 PG, CodeDeploy 실행 경계를 분리합니다.

  6. 06

    운영·복구

    중복 과금, stale processing, PG 성공 후 DB 실패를 DB 상태·Outbox·worker 로그 기준으로 복구합니다.

01 · Requirement Cases

결제·구독 도메인의 요구사항을 케이스 단위로 나눠 분석했습니다

이 프로젝트의 핵심은 “결제 기능 구현” 하나가 아니라, 영상 접근, 단건 구매, 최초 구독 결제, 정기 갱신, 플랜 변경·해지를 각각 다른 요구사항 케이스로 분석한 뒤 하나의 서비스 경험으로 연결하는 것이었습니다. 결제와 구독 생명주기도 영상 접근 정책과 같은 레벨의 요구 분석 대상입니다.

  • 영상 접근 요구는 콘텐츠·상품·권한 정책을 분리한 케이스입니다.
  • 단건 결제 요구는 서버 가격 재검증과 수강권 부여를 분리한 케이스입니다.
  • 최초 구독 결제 요구는 빌링키 준비와 첫 유료 결제 활성화를 분리한 케이스입니다.
  • 정기 갱신 요구는 중복 과금 방어와 PG 성공 후 내부 확정 복구를 분리한 케이스입니다.
  • 플랜 변경·해지 요구는 가격 비교, 적용 시점, 다음 갱신 차단을 분리한 케이스입니다.
  • 각 케이스는 요구 분석 → 도메인 모델링 → 아키텍처 결정 → 구현·검증 → 배포·인프라 → 운영·복구 흐름으로 다시 추적할 수 있게 배치했습니다.
  1. 01

    영상 상품·구독 접근

    영상 1개를 콘텐츠 단위로 잡고, 구독 상품별 영상 길이 접근 조건을 활성 정책으로 평가합니다.

  2. 02

    단건 결제·수강권

    장바구니·바로 결제 요구를 구매 의도, 서버 가격 재검증, PG 승인, 단건 수강권 부여로 분리합니다.

  3. 03

    최초 구독 결제

    구독 시작을 첫 과금 완료가 아니라 Order, Subscription, Invoice, billing-key 준비 상태가 맞물리는 흐름으로 봅니다.

  4. 04

    정기 갱신·복구

    매월 청구 회차, worker 선점, PG 승인, 내부 finalize, 실패 재시도를 서로 다른 상태 전이로 나눕니다.

  5. 05

    플랜 변경·해지

    업그레이드, 다운그레이드, 기간말 해지, 재개를 가격 비교와 적용 시점 정책으로 분리합니다.

요구사항을 기능명이 아니라 상태 변화로 나눔

선택

각 요구를 “무엇이 새로 생기고, 무엇이 확정되고, 무엇을 다시 검증해야 하는가” 기준으로 별도 케이스로 분류했습니다.

문제
사용자 화면에서는 구매, 구독 시작, 갱신, 변경, 시청이 한 서비스처럼 보이지만 서버에서는 바뀌는 사실과 실패 비용이 모두 달랐습니다.
이유
영상 접근 정책을 설명하다가 결제 생명주기가 가려지거나, 반대로 PG 연동 설명에 권한 정책이 묻히는 문제를 피할 수 있습니다.

결제·구독 생명주기도 독립 요구사항으로 둠

선택

단건은 수강권 부여, 최초 구독은 billing-key와 활성화, 갱신은 청구 회차와 중복 과금 방어, 플랜 변경은 적용 시점 정책으로 나눴습니다.

문제
단건 결제, 최초 구독, 정기 갱신, 플랜 변경은 모두 PG를 호출하지만 생성되는 도메인 사실과 복구 지점이 다릅니다.
이유
한 Processor나 한 상태 컬럼에 모든 결제 흐름을 밀어 넣지 않아 요구 변경과 장애 복구 지점이 선명해집니다.

각 케이스를 문서·코드·커밋으로 따로 검증

선택

케이스별로 원천 문서, 구현 심볼, 커밋 신호, 공개 가능한 회고 링크를 따로 묶어 검증했습니다.

문제
포트폴리오에서는 “내가 그렇게 생각했다”가 아니라 실제 프로젝트에서 그런 방식으로 일했는지 보여줘야 합니다.
이유
검수자가 깊게 들어가지 않아도 구조를 먼저 이해하고, 필요하면 특정 케이스의 근거로 내려갈 수 있습니다.
읽는 순서

이 섹션은 프로젝트 안의 요구사항 목록을 먼저 정규화한 지도입니다. 이후 섹션들은 각 케이스가 모델 책임, PG 경계, 구현 검증, 배포 경계, 운영 복구 기준으로 어떻게 이어졌는지 보여줍니다.

01-A · Requirement Case

케이스 A: 영상 상품과 구독 접근 조건을 별도 요구사항으로 분석했습니다

이 프로젝트의 요구사항 큐에는 단건 결제, 최초 구독 결제, 정기 갱신, 플랜 변경, 해지·재개도 있었고, “어떤 영상이 어떤 구독으로 볼 수 있는가”도 별도 요구사항으로 있었습니다. 이 케이스에서는 콘텐츠 단위, 상품 단위, 결제 단위, 시청 권한 단위가 서로 다르다는 점을 먼저 분석했습니다.

  • 기존 LMS식 강의/섹션 계층보다 “영상 1개 = 콘텐츠 1단위”가 제품 스코프에 맞다고 판단했습니다.
  • 영상 목록의 구독 안내는 구매 유도 정보이고, 실제 시청 허가는 서버가 현재 사용자 상태와 활성 정책으로 다시 판단해야 했습니다.
  • 구독 상품 카드에는 내부 길이 제한 값을 직접 노출하지 않고, 서버가 혜택 라벨과 포함 여부를 파생해 내려주도록 정리했습니다.
  • 정책 없는 구독 상품은 노출하지 않고, 정책 조건 변경은 다음 요청부터 목록 정렬·혜택·재생 권한에 반영되도록 요구를 고정했습니다.
  1. 01

    영상 상품

    영상 1개를 콘텐츠와 판매의 기본 단위로 보고, 무료·구독·스페셜 접근 유형과 길이 정보를 함께 다룹니다.

  2. 02

    구독 상품

    구독 상품은 결제할 수 있는 월정액 상품이지만, 실제 권한은 상품명이나 티어 문자열이 아니라 접근 정책으로 판단합니다.

  3. 03

    접근 조건

    영상 길이를 정책 조건으로 두고, 각 구독 상품이 어느 길이의 영상을 허용하는지 서버가 계산합니다.

  4. 04

    요청 시점 제한

    사용자 구독에 권한 값을 복사하지 않고 요청 시점의 활성 정책을 평가해 목록·상세·재생 권한을 제한합니다.

요구를 “상품 판매”가 아니라 “시청 가능 여부” 질문으로 바꿈

선택

영상 상품, 구독 상품, 단건 수강권, 활성 구독, 접근 정책을 각각 다른 판단 재료로 분리했습니다.

문제
영상 목록, 구독 상품 카드, 결제 화면은 모두 상품처럼 보이지만 사용자가 실제로 궁금한 것은 “내가 지금 이 영상을 볼 수 있는가”였습니다.
이유
구매 유도 문구와 실제 접근 허가를 섞지 않아 프론트 표시 오류가 권한 우회로 이어지지 않습니다.

구독 등급명을 권한 기준으로 쓰지 않음

선택

구독 상품은 판매 단위로 두고, “몇 초 이하 영상을 볼 수 있는가”는 활성 접근 정책의 조건으로 모델링했습니다.

문제
Basic, Silver 같은 이름은 운영자가 바꿀 수 있는 표시 정보이고, 영상 길이 제한은 정책으로 바뀌어야 하는 조건이었습니다.
이유
등급명 변경, 문구 변경, 권한 조건 변경이 서로 독립되어 유지보수 비용이 줄어듭니다.

정책 변경이 다음 요청부터 반영되게 함

선택

사용자 구독에 권한 값을 복사하지 않고 목록·상세·재생 시점마다 현재 활성 정책과 영상 길이를 다시 평가했습니다.

문제
구독별 접근 길이가 바뀔 때 기존 사용자 구독 데이터를 일괄 수정하면 누락·불일치·배포 리스크가 생깁니다.
이유
운영자가 접근 정책을 조정해도 기존 구독 row를 마이그레이션하지 않고 사용자 접근 제한을 다음 서버 요청부터 일관되게 바꿀 수 있습니다.

Trade-off과거 시점 권한 판정의 감사가 필요하면 별도 정책 버전 기록이나 평가 로그가 필요합니다.

이 케이스의 위치

이 섹션은 결제·구독 생명주기를 대체하는 중심 서사가 아니라, 같은 프로젝트 안에서 따로 풀어야 했던 요구사항 분석 사례 중 하나입니다. “사용자가 이 영상을 볼 수 있는가?”는 영상 접근 유형, 영상 길이, 활성 구독, 스페셜 수강권, 현재 활성 접근 정책을 함께 평가해야 합니다.

02 · Domain Model

영상·구독 접근 모델과 결제 상태 모델을 서로 다른 책임으로 분리했습니다

영상 상품과 구독 상품은 같은 판매 상품처럼 보이지만, 영상은 콘텐츠 메타와 접근 유형을 갖고 구독은 접근 정책과 반복 청구를 갖습니다. 단건 구매와 구독 갱신도 사용자 경험과 회계 의미가 달라 한 모델에 몰아넣지 않았습니다.

  1. 01

    ProductVideo

    영상 메타, 카테고리, 길이, 무료·구독·스페셜 접근 유형을 담당합니다.

  2. 02

    SubscriptionProduct

    월정액으로 판매되는 구독 상품의 확장 정보이며, 권한 값 자체는 들고 있지 않습니다.

  3. 03

    Access Policy

    구독 상품과 활성 정책을 연결하고, 영상 길이 조건은 PolicyRule의 술어로 평가합니다.

  4. 04

    Order

    사용자가 결제 버튼을 눌러 만든 최초 구매 계약·영수증 단위입니다. 단건과 구독 최초 구매에만 존재합니다.

  5. 05

    SubscriptionInvoice

    INITIAL·RENEWAL·PLAN_CHANGE 등 구독의 청구 회차와 과금 기간을 기록합니다.

  6. 06

    PaymentIntent

    PG 결제 시도와 승인 전 중간 상태, useCase, 대상 주문·청구서를 기록합니다.

  7. 07

    Payment

    실제로 이동한 돈과 PG 거래 ID, 결제수단 스냅샷을 보존합니다.

핵심 불변 조건

구독 상품명은 권한 판정 기준이 아니고, 구독 권한은 활성 접근 정책으로 동적으로 계산합니다. Order는 구매 의도, Invoice는 청구 회차, PaymentIntent는 PG 시도, Payment는 실제 승인 결과를 담당합니다.

03 · Access Policy

영상 길이 기반 접근 조건을 정책 룰로 일반화해 변경 가능하게 만들었습니다

구독 상품별 권한을 사용자 구독에 복사하면 정책 변경 때마다 기존 사용자의 상태를 대량 수정해야 합니다. 대신 구독 상품은 활성 접근 정책을 참조하고, 영상 길이 조건은 정책 룰로 평가하도록 모델링했습니다.

  • 영상 길이 조건은 내부 정렬·혜택 파생·시청 판정에 사용하고, 구독 상품 응답에는 raw 제한 값을 노출하지 않았습니다.
  • 활성 접근 정책이 없는 구독 상품은 목록에서 제외해 “팔 수 있지만 권한이 정의되지 않은 상품”을 사용자에게 노출하지 않았습니다.
  • 무료 영상, 스페셜 단건 구매 영상, 구독 영상은 같은 영상 상품이지만 권한 판정 경로를 다르게 처리했습니다.
  • 구독은 있지만 영상 길이 한도를 넘는 경우를 별도 차단 사유로 분리해 업그레이드 유도와 접근 제한을 동시에 설명할 수 있게 했습니다.

권한 값을 사용자 구독에 스냅샷하지 않음

선택

사용자의 활성 구독은 현재 상품을 가리키고, 실제 접근 가능 여부는 요청 시점의 활성 접근 정책과 영상 길이로 평가했습니다.

문제
구독 상품의 허용 영상 길이가 바뀔 때 사용자 구독 row를 모두 수정하면 변경 비용과 불일치 위험이 커집니다.
이유
정책 변경이 다음 목록·상세·재생 요청부터 반영되어 운영자가 상품 정책을 바꾸기 쉽습니다.

Trade-off과거 어느 정책으로 시청했는지 감사가 필요하면 정책 버전과 평가 로그를 별도로 남겨야 합니다.

표시용 구독 안내와 실제 시청 허가를 분리

선택

목록에서는 현재 영상 길이를 만족하는 최소 구독 후보만 표시하고, 상세·재생 시에는 사용자 상태와 정책을 다시 평가했습니다.

문제
영상 목록의 “필요 구독” 표시는 구매 유도 정보이고, 실제 시청 허가와 동일하지 않습니다.
이유
프론트 표시값을 권한 정본으로 오해하지 않게 하고, 비로그인·구독 없음·구독 한도 초과를 각각 다른 차단 사유로 설명할 수 있습니다.

정책 룰을 확장 지점으로 둠

선택

접근 조건을 정책 룰의 key/operator/value 형태로 두고 evaluator가 해석하도록 했습니다.

문제
초기 요구는 영상 길이였지만 이후 카테고리, 상품, 기간 같은 조건이 추가될 수 있습니다.
이유
새 조건을 추가해도 구독 상품과 결제 모델을 다시 설계하지 않고 evaluator와 정책 데이터 확장으로 대응할 수 있습니다.
확장성과 유지보수성

접근 조건을 구독 상품명이나 사용자 구독 row에 박아두지 않고 정책 룰과 evaluator에 모았습니다. 그래서 영상 길이 외 조건이 추가되어도 결제·구독 모델을 다시 만들지 않고, 정책 조건 변경은 기존 사용자 데이터를 마이그레이션하지 않은 채 다음 목록·상세·재생 요청부터 반영할 수 있습니다.

관련 설계 회고
구매 사실과 시청 권한을 분리한 Entitlement 설계단건 구매 수강권과 구독 정책 기반 권한을 서로 다른 수명주기로 나눈 회고LMS 강의 계층을 단일 영상 상품으로 평탄화한 과정영상 1개를 콘텐츠·상품·접근 판정 단위로 다시 잡은 도메인 재설계 회고

PG를 클라이언트가 선택하지 않게 함

선택

서버가 확정한 ProductPrice의 통화·사용 유형·결제수단으로 PaymentRoute를 조회했습니다.

문제
클라이언트 입력을 신뢰하면 가격·통화·계약과 맞지 않는 PG를 호출할 수 있습니다.
이유
라우팅 정책을 운영 데이터로 관리하고 요청 변조를 차단할 수 있습니다.

Vendor 응답을 도메인까지 전달하지 않음

선택

Adapter와 Mapper에서 공통 PaymentApproveResult로 정규화한 뒤 Processor에 전달했습니다.

문제
PG마다 필드명, 성공 코드, callback 시점, 빌링키 구조가 다릅니다.
이유
주문·구독 상태 전이 코드는 PG에 의존하지 않고 재사용됩니다.

05 · Pricing Snapshot

가격 정책과 계산 근거를 결제 시점 스냅샷으로 동결했습니다

결제 금액은 클라이언트가 전달한 숫자가 아니라 서버가 알고 있는 상품 가격, 통화, 사용 유형, 정책 규칙에서 계산되어야 했습니다. 계산 결과는 이후 환불·대사·문의 대응을 위해 주문과 결제 시점에 남겨야 했습니다.

  • ProductPrice는 표시 가격이 아니라 결제 라우팅과 청구 금액의 기준 데이터로 다뤘습니다.
  • PaymentRoute는 currency, usageType, method를 조합해 어떤 PG를 호출할지 서버에서 결정하게 했습니다.
  • 정책 변경 가능성이 있는 값과 과거 주문에 고정되어야 하는 값을 분리했습니다.
  • 가격 계산 회고와 실제 결제 모델 섹션을 연결해 “왜 이 모델이 필요한가”를 먼저 설명합니다.

클라이언트 금액을 신뢰하지 않음

선택

서버의 ProductPrice와 적용 가능한 정책을 기준으로 결제 금액을 다시 계산했습니다.

문제
프론트에서 전달한 amount를 그대로 PG에 넘기면 가격 변경, 통화 오류, 요청 변조를 구분하기 어렵습니다.
이유
금액 결정의 정본을 서버에 두면 PG 호출 전 검증과 운영 대사가 같은 기준을 사용합니다.

정책 결과를 주문에 남김

선택

계산된 가격, 통화, 사용 유형, 정책 적용 결과를 주문·청구 시점의 스냅샷으로 보존했습니다.

문제
결제 이후 상품 가격이나 프로모션 정책이 바뀌면 과거 주문의 금액 근거가 사라질 수 있습니다.
이유
나중에 환불, 영수증, 고객 문의를 처리할 때 현재 정책이 아니라 당시 결제 근거를 기준으로 설명할 수 있습니다.
관련 설계 회고
가격 계산 근거를 주문에 동결한 정책 설계클라이언트 금액을 신뢰하지 않고 가격 정책·계산 결과·스냅샷을 분리한 회고

06 · Initial Subscription

동기·비동기 PG의 최초 구독 결제를 하나의 상태 모델로 수렴시켰습니다

  1. 01

    서버 상태 생성

    Order(PENDING), Subscription(INCOMPLETE), Invoice(INITIAL/OPEN)를 먼저 만들고 멱등키와 요청 해시를 저장합니다.

  2. 02

    빌링키 준비

    NICEPAY는 동기 발급, Payletter는 결제창과 callback에서 토큰을 받아 PENDING_CONFIRM 상태로 암호화 저장합니다.

  3. 03

    첫 유료 결제

    준비된 빌링키로 PG를 청구하고 정규화된 결과를 Initial Processor에 전달합니다.

  4. 04

    원자적 활성화

    Order·Subscription·Invoice·BillingKey 상태를 완료하고 PaymentIntent·Payment·Outbox를 한 트랜잭션에서 생성합니다.

비동기 callback 순서 역전 대응

브라우저 return이 Payletter billing-key callback보다 먼저 도착하면 WAITING_BILLING_KEY를 반환하고, Outbox worker가 키 준비 여부를 재시도하도록 했습니다.

07 · Renewal Reliability

구독 갱신에서 중복 과금과 부분 성공을 별도로 다뤘습니다

겹치지 않는 self-rescheduling 루프

선택

한 회차가 완료된 뒤 다음 실행을 예약하고, backlog가 있으면 짧은 간격으로 다음 chunk를 처리했습니다.

문제
고정 Cron이 이전 회차가 끝나기 전에 재실행되면 같은 프로세스에서도 중복 작업이 생길 수 있습니다.
이유
정상 주기와 밀린 작업 처리 속도를 분리하면서 같은 프로세스의 실행 겹침을 막습니다.

회차 선점과 DB 백스톱

선택

subscription 행을 FOR UPDATE로 잠그고 RENEWAL invoice와 intent를 PROCESSING으로 선점했습니다.

문제
다중 인스턴스가 같은 subscription을 동시에 조회할 수 있습니다.
이유
한 워커만 PG 호출 권한을 얻고, 동일 subscription + period의 부분 유일 인덱스로 최종 중복 생성도 차단합니다.

PG 호출과 DB 트랜잭션 분리

선택

청구 상태 선점 후 트랜잭션을 커밋하고, PG 호출은 밖에서 실행한 뒤 성공·실패 확정만 새 트랜잭션으로 처리했습니다.

문제
느린 외부 네트워크 호출을 트랜잭션 안에 두면 잠금 시간이 길어집니다.
이유
락 범위를 줄이면서 중복 청구 방어 상태는 DB에 남깁니다.

Trade-offPG 성공 후 DB 확정 실패라는 부분 성공이 생기므로 별도 복구 경로가 필요합니다.

재과금 없는 finalize retry

선택

PG 거래 ID를 포함한 Outbox를 만들고, 같은 결제를 다시 호출하지 않고 내부 finalize 트랜잭션만 재시도했습니다.

문제
PG 승인 성공 뒤 DB 확정이 실패했을 때 일반 재시도는 사용자를 다시 과금할 수 있습니다.
이유
외부 금전 이동과 내부 상태를 안전하게 대사할 수 있습니다.
관련 설계 회고
PG 승인 이후 DB 확정 실패를 재결제 없이 복구한 과정부분 성공을 외부 결제 사실과 내부 finalize 단계로 나눈 구독 갱신 회고

08 · Subscription Lifecycle

갱신 실패·플랜 변경·해지와 시청 권한을 서로 다른 정책으로 분리했습니다

  • 갱신 실패 시 PAST_DUE와 nextRetryAt을 남기고 최대 4회까지 재시도한 뒤 UNPAID로 이용을 정지했습니다.
  • 접근 유예 시간은 운영 변경 가능성을 고려해 PolicyRule로 관리했습니다.
  • 업그레이드는 결제 성공 후 적용하고, 다운그레이드는 현재 기간 종료 시점에 예약 적용했습니다.
  • 기간말 해지는 현재 기간 이용권을 유지하고 다음 갱신만 차단한 뒤, 갱신 루프 선행 단계에서 실제 종료를 확정했습니다.
  • 월 구독 기간은 30일 고정이 아니라 최초 anchor의 달력 월·말일 보정 규칙으로 계산했습니다.
  • 구독 상품명, 결제 상태, 영상 접근 정책을 분리하고, 활성 접근 정책을 요청 시점에 평가했습니다.
관련 설계 회고
구매 사실과 시청 권한을 분리한 Entitlement 설계단건 구매·구독 정책·시청 이력의 수명주기를 분리한 상세 회고LMS 강의 계층을 단일 영상 상품으로 평탄화한 과정카탈로그·상품·접근 방식의 책임을 다시 나눈 도메인 재설계 회고

09 · Runtime & Delivery

결제·구독 도메인을 API, worker, DB, Redis, 외부 연동 경계로 운영했습니다

결제 요청은 동기 API에서 검증하고, 갱신·알림·부분 성공 복구처럼 재시도 가능한 작업은 worker와 queue 경계로 분리했습니다. 배포는 아티팩트 생성, CodeDeploy, 프로세스 reload, readiness 확인 순서로 운영 기준을 잡았습니다.

  • 긴 외부 결제 호출은 DB 트랜잭션 밖으로 빼고, 내부 확정 단계만 짧은 트랜잭션으로 처리했습니다.
  • PG 승인 뒤 내부 확정 실패는 Outbox worker가 재과금 없이 finalize만 다시 수행하도록 분리했습니다.
  • 구독 갱신은 worker 실행 경계에서 처리하고, DB 잠금과 유일성 제약으로 다중 인스턴스 중복 과금을 방어했습니다.
  • 첨부·이미지는 DB에 공개 URL을 저장하지 않고 storage key/path를 정본으로 두는 운영 원칙을 따랐습니다.
  • DB migration은 배포 전 SQL 검토 대상이고, 배포 후에는 readiness와 핵심 결제 흐름을 smoke 기준으로 확인했습니다.

10 · Operations Evidence

결제 운영 가능성은 리뷰·런북·상태 기준으로 검증했습니다

결제 프로젝트의 운영 근거는 성공률 숫자를 꾸미는 방식이 아니라, 어떤 핵심 수치를 어떤 상태로 기록했고 실패했을 때 어느 문서와 실행 경계로 복구할 수 있는지를 확인하는 방식으로 정리했습니다.

  • PG별 완료·부분 구현·미구현 범위를 구현 상태 감사 문서와 회귀 테스트 기준으로 구분했습니다.
  • 결제·구독 도메인의 핵심 수치는 처리량 과장이 아니라 “몇 개의 외부 PG와 요구 케이스를 어떤 상태 모델로 통제했는가”를 보여주는 증거로만 사용합니다.
  • Outbox, queue, 갱신 worker, CodeDeploy, readiness 확인은 운영 중 복구 가능한 경계를 설명하는 근거로 사용합니다.
  • Prisma migration SQL은 배포 전 검토 대상으로 두고, 스키마 변경과 결제 상태 전이가 충돌하지 않도록 확인했습니다.
  • 정확한 PG 성공률, p95, 오류율은 공개 가능한 운영 로그가 없어 정량 성과로 쓰지 않습니다.
  1. 01

    기능 범위 수치

    2개 PG, 5개 요구 케이스, 단건·구독·갱신·변경 흐름은 프로젝트 범위를 설명하는 수치로만 사용합니다.

  2. 02

    정책 수치

    갱신 실패 4회, 회차별 1건 선점 같은 값은 성공 성과가 아니라 운영 정책과 정합성 제약의 기준으로 기록합니다.

  3. 03

    상태 근거

    Order, Invoice, PaymentIntent, Payment, Subscription, Outbox 상태를 기준으로 멈춘 지점과 재처리 범위를 판단합니다.

  4. 04

    미보유 수치

    PG 성공률, p95, 오류율처럼 원본 운영 로그가 필요한 지표는 공개 가능한 근거가 없어 성과 수치로 쓰지 않습니다.

운영 근거의 기준

이 섹션은 “운영 지표가 얼마나 좋았는가”보다 “프로젝트에서 기록한 상태와 정책 수치로 실패를 어디서부터 복구할 수 있는가”를 보여주는 카드입니다.

11 · Outcome & Review

영상 접근 정책은 변경 가능하게, PG 실패는 복구 가능하게 남겼습니다

  • 영상 상품, 구독 상품, 접근 정책, 단건 수강권을 분리해 영상 길이 기반 권한 변경을 결제 모델과 독립적으로 다룰 수 있게 했습니다.
  • NICEPAY와 Payletter를 동일한 주문·청구·결제 모델과 Processor 흐름으로 연결했습니다.
  • 단건 구매, 최초 구독, 정기 갱신, 플랜 변경, 기간말 해지를 실제 런타임에 구현했습니다.
  • 중복 요청·다중 워커·stale processing·과금 성공 후 DB 실패에 각각 다른 방어와 복구 경로를 적용했습니다.
  • 회귀 테스트와 구현 상태 감사 문서로 완료·부분 구현·미구현 범위를 구분했습니다.
미구현 범위

구독 환불과 일부 proration 기반 정책은 최종 서비스 범위에 포함되지 않았습니다. 포트폴리오에서도 구현 완료로 표기하지 않습니다.

Outcome

확인 가능한 결과

  • 국내·해외 카드 결제와 단건·구독 청구를 공통 도메인 모델로 운영
  • 최초 결제·갱신·실패 재시도·플랜 변경·기간말 해지의 구독 수명주기 구현
  • 행 잠금·회차 선점·DB 유일성 제약으로 중복 과금 방어
  • PG 성공 후 DB 실패를 재과금 없이 복구하는 Outbox finalize retry 구현

Limitations

한계와 미구현 범위

  • 구독 환불은 단건 주문 환불 도메인과 연결되지 않아 미구현입니다.
  • 정책 모델에 proration 계산 구조는 있으나 최종 제품 정책은 새 플랜 정가 재시작을 사용했습니다.
  • PG별 운영 성공률·처리량 지표는 공개 가능한 운영 자료가 없어 정량 성과로 사용하지 않습니다.
Confidentiality

회사·서비스·가맹점 식별 정보와 내부 API 경로는 일반화하고, 공개 가능한 모델·결정·복구 전략만 설명합니다.
