Production Case Study 05

레거시 리뉴얼과 도메인 재설계

어테일 생애설계 플랫폼에서 큐레이션 콘텐츠와 사용자 목표 데이터를 분리하고, 템플릿→인스턴스 패턴, 목표 위계, 카테고리·콘텐츠 그래프, Express/TypeORM 계층 구조를 재정리했습니다.

Ownership

직접 담당한 범위

  • 생애설계 콘텐츠 플랫폼의 Express/TypeORM 백엔드 도메인 모델·API·DB 구조 설계
  • 큐레이션 목표·아티클·영상 템플릿과 사용자 목표 인스턴스의 생명주기 분리
  • Goal→Task→Daily 목표 위계, 8대 영역·세부 카테고리, 해시태그·콘텐츠 그래프 모델링
  • 운영 중인 enum성 분류를 테이블 기반 카테고리로 옮기는 방향과 soft delete 조회 기준 정리

Constraints

먼저 해결해야 했던 제약

  • 운영자가 편집하는 큐레이션 원본과 사용자가 진행·편집하는 개인 목표는 같은 테이블에 둘 수 없었습니다.
  • 사용자가 목표를 “시작”하는 행위와 콘텐츠를 “담아두는” 행위는 저장 비용과 최신성 요구가 달랐습니다.
  • 8대 생애 영역과 세부 카테고리는 코드 enum보다 운영 데이터로 관리될 필요가 있었습니다.
  • 아카이브에는 활성 엔티티와 주석 처리된 설계 흔적이 섞여 있어 구현 완료와 미활성 설계를 구분해야 했습니다.

Project Overview

운영자가 만든 큐레이션 콘텐츠를 사용자 목표로 전환하는 데이터 구조를 재설계했습니다

어테일은 사용자가 생애 영역별 목표를 세우고, 운영자가 만든 추천 목표·아티클·영상을 자기 계획으로 가져오는 서비스였습니다. 핵심은 콘텐츠 원본과 사용자 진행 데이터를 섞지 않으면서도 출처와 연결 관계를 잃지 않는 것이었습니다.

  • 서비스 관점에서는 큐레이션 원본을 여러 사용자가 안전하게 가져가고 개인화할 수 있어야 했습니다.
  • 데이터 관점에서는 사용자 편집이 원본 템플릿을 오염시키지 않도록 생명주기를 분리해야 했습니다.
  • 검증 범위는 아카이브된 Express/TypeORM 소스와 사후 재구성 architecture/ADR 문서를 기준으로 합니다.
  1. 01

    Curation

    운영자가 추천 목표, 아티클, 영상 템플릿을 만들고 계속 편집합니다.

  2. 02

    Instance

    사용자가 추천 목표를 시작하면 편집 가능한 개인 목표로 복제합니다.

  3. 03

    Bookmark

    편집하지 않고 담아두는 콘텐츠는 복합 PK 조인으로 연결만 남깁니다.

  4. 04

    Hierarchy

    개인 목표는 Goal→Task→Daily 단계로 구체화됩니다.

  5. 05

    Taxonomy

    8대 영역과 세부 카테고리는 테이블 기반 분류로 옮기는 방향을 잡았습니다.

01 · Renewal

레거시 리뉴얼 요구를 콘텐츠 원본, 사용자 인스턴스, 운영 분류 문제로 나눴습니다

  • 운영자 큐레이션 콘텐츠는 여러 사용자에게 공통 노출되고 계속 편집되므로 사용자 목표와 생명주기가 다릅니다.
  • 사용자가 추천 목표를 실제 목표로 시작하면 제목, 기간, 예산, 완료 여부가 개인별로 달라집니다.
  • 아티클이나 추천 목표를 단순 저장하는 행위는 복제보다 연결이 적합하므로 별도 조인 모델이 필요했습니다.
  • 카테고리와 해시태그는 콘텐츠 탐색과 목표 분류를 함께 담당하므로 테이블·조인 그래프로 분리했습니다.

02 · Template to Instance

큐레이션 원본과 사용자 소유 목표를 복제·연결 두 경로로 분리했습니다

같은 “가져오기”처럼 보여도, 추천 목표를 내 목표로 시작하는 행위와 콘텐츠를 담아두는 행위는 다릅니다. 전자는 편집 가능한 사본이 필요하고, 후자는 원본 최신성을 유지하는 연결이 더 적합했습니다.

  1. 01

    Template content

    운영자가 관리하는 추천 목표·아티클·영상 원본입니다.

  2. 02

    Copy instance

    시작한 추천 목표는 사용자 소유 Goal로 복제하고 출처 템플릿을 남깁니다.

  3. 03

    Bookmark relation

    담아둔 목표·아티클은 복합 PK 조인 엔티티로 관계만 기록합니다.

  4. 04

    Editable lifecycle

    복제된 목표는 태스크·데일리·완료·soft delete 생명주기를 따릅니다.

핵심 불변 조건

운영자 큐레이션 원본은 사용자 편집으로 오염되면 안 되고, 사용자 목표는 어느 템플릿에서 시작됐는지 provenance를 잃으면 안 됩니다.

관련 설계 회고
큐레이션 템플릿의 복제와 북마크를 분리한 모델링원본 템플릿과 사용자 목표 인스턴스의 수명주기를 나눈 회고

03 · Hierarchy & Taxonomy

목표 위계와 카테고리, 콘텐츠 그래프를 서로 다른 변경 축으로 분리했습니다

활성 위계는 Goal→Task→Daily로 제한

선택

공개 설명에서는 활성 엔티티로 확인되는 Goal→Task→Daily 위계를 기준으로 삼았습니다.

문제
소스에는 더 큰 생애 비전 모델 흔적이 있지만 파일 전체가 주석 처리되어 런타임 근거로 보기 어렵습니다.
이유
설계 의도와 구현 완료 범위를 섞지 않아 면접에서 방어 가능한 설명이 됩니다.

8대 영역은 enum이 아니라 테이블 기반 분류로 해석

선택

카테고리 변경 가능성을 고려해 운영 데이터 기반 taxonomy로 설명했습니다.

문제
영역 enum 파일은 주석 처리되어 있고, 영역·세부 카테고리 엔티티가 활성화되어 있습니다.
이유
앱 구동 시 변경된 카테고리 목록을 내려주는 방향과 맞고, 코드 배포 없는 분류 변경 가능성을 열어 둡니다.

해시태그와 콘텐츠 묶음은 조인 엔티티로 통일

선택

복합 PK 조인 엔티티를 사용해 콘텐츠 그래프를 일관된 패턴으로 구성했습니다.

문제
목표, 추천 목표, 영상, 아티클은 서로 다른 콘텐츠지만 태그와 큐레이션 묶음을 공유합니다.
이유
콘텐츠 타입이 늘어도 같은 조인 관용구로 확장할 수 있습니다.

04 · Layered Architecture

Express 위에서 Router→Controller→Service→Repository→Entity 흐름을 직접 나눴습니다

프레임워크가 계층을 강제하지 않는 Express 환경이었기 때문에, 도메인별 라우터와 TypeDI 서비스, TypeORM 리포지토리, 엔티티를 수동 컨벤션으로 분리했습니다.

NestJS가 아닌 Express에서도 컨트롤러·서비스·리포지토리 경계를 명시해, 도메인 로직이 라우터와 엔티티에 흩어지지 않도록 구성했습니다.

05 · Implementation Evidence

활성 구현, 주석 처리된 설계, 공개 불가 근거를 분리해 검증했습니다

  • 엔티티 파일 31개 중 활성 엔티티 23개와 주석 처리된 설계 흔적 8개를 구분했습니다.
  • 템플릿→사용자 목표 복제, 사용자–템플릿/아티클 연결, 해시태그·콘텐츠 그래프는 실제 엔티티·관계로 확인했습니다.
  • 라우터 계층은 인증, DTO 검증, 비동기 에러 처리 미들웨어를 통해 요청 경계를 명시했습니다.
  • 비활성 Vision, UserKeyword, CompositeAsset, ReportImage는 설계 흔적으로만 남기고 구현 완료 범위로 표현하지 않았습니다.
내용 검증 기준

활성 TypeORM 데코레이터, 주석 처리 여부, architecture/data-model/ADR 문서가 서로 일치하는 내용만 프로젝트 상세에 반영했습니다.

06 · Migration & Release

레거시 전환은 데이터 마이그레이션과 조회 경로 검증을 릴리스 단위로 다뤘습니다

이 프로젝트는 현재 공개 가능한 배포 인프라 로그가 남아 있지 않습니다. 대신 레거시 데이터를 신규 도메인 모델로 옮기고, API 전환과 주요 조회 경로를 함께 검증한 전환 구조까지만 공개합니다.

  • 기존 데이터 구조와 신규 도메인 모델의 매핑을 먼저 정리하고, 마이그레이션과 API 전환을 같은 릴리스 위험으로 다뤘습니다.
  • 파일·이미지 경로는 S3 기반 저장소를 전제로 모델링되어 있으며, 도메인 엔티티에는 공개 URL 성격의 값만 남았습니다.
  • Docker/ECR 스크립트 흔적은 있으나 실제 배포 로그와 운영 절차 원본은 공개 가능한 자료로 확인하지 못했습니다.
  • 배포 도구, 서버 토폴로지, 운영 로그는 현재 검증 가능한 원천 자료가 부족해 구체 인프라 구성으로 표기하지 않습니다.
없는 근거는 없다고 남깁니다

레거시 프로젝트는 마이그레이션·API 전환·조회 구조 개선 근거는 있지만, 배포 파이프라인과 서버 구성 원천 자료가 부족합니다. 그래서 인프라 스택을 상상해서 채우지 않습니다.

07 · Operations Evidence

운영 가능성은 soft delete, 분류 테이블, 민감 필드 경계처럼 코드에 남은 기준으로만 설명합니다

삭제는 물리 삭제보다 soft delete 기준으로 읽음

선택

삭제된 목표와 콘텐츠가 조회되지 않도록 soft delete 조회 조건을 운영 기준으로 보았습니다.

문제
Goal, Task, Daily, 콘텐츠 엔티티는 사용자 흐름과 운영 조회에서 삭제 여부를 구분해야 합니다.
이유
사용자에게는 제거되지만 원본과 이력의 정합성을 잃지 않습니다.

민감 필드는 응답 DTO 경계가 필요

선택

공개 포트폴리오에서는 엔티티를 그대로 응답하지 않는 경계의 필요성을 한계로 함께 표기합니다.

문제
사용자 엔티티에는 비밀번호 해시와 refresh token 같은 민감 정보가 포함됩니다.
이유
초기 코드의 구조를 설명하면서도 보안상 주의해야 할 지점을 숨기지 않습니다.

운영 지표는 만들지 않음

선택

성능 개선 수치 대신 모델링·전환 구조와 미보존 지표를 분리해 적었습니다.

문제
당시 응답시간, 장애율, 트래픽 로그는 현재 보존된 검증 원본이 없습니다.
이유
검증되지 않은 수치를 쓰지 않는 것이 오래된 프로젝트의 신뢰도를 높입니다.

08 · Outcome & Review

레거시 리뉴얼 경험은 도메인 책임 분리와 검증 범위 표시까지 함께 보여줍니다

  • 큐레이션 콘텐츠와 사용자 데이터의 생명주기를 분리한 템플릿→인스턴스 모델을 정리했습니다.
  • Goal→Task→Daily 위계, 8대 영역 분류, 콘텐츠 조인 그래프를 활성 코드 기준으로 설명했습니다.
  • Express/TypeORM 환경에서 계층 경계를 직접 나눈 구조를 프로젝트 상세 흐름에 연결했습니다.
  • 비활성 설계와 미보존 운영 지표는 한계로 명시해 과거 프로젝트를 과장하지 않았습니다.

Outcome

확인 가능한 결과

  • 템플릿→사용자 목표 인스턴스 복제와 북마크 연결을 분리한 데이터 모델 정리
  • Goal→Task→Daily 목표 위계와 카테고리·콘텐츠 그래프 모델링
  • Express/TypeORM/TypeDI 기반 Router→Controller→Service→Repository→Entity 계층 구조 구성
  • 활성 엔티티와 미활성 설계 흔적을 분리해 공개 가능한 구현 범위 정리

Limitations

한계와 미구현 범위

  • 원본 서비스 코드와 내부 데이터는 공개하지 않습니다.
  • 당시 측정 로그가 현재 검증 가능한 원본으로 남아 있지 않아 응답시간 개선 수치는 사용하지 않습니다.
  • Vision, UserKeyword, CompositeAsset, ReportImage 등 주석 처리된 설계는 구현 완료로 표기하지 않습니다.
  • 배포 파이프라인과 서버 토폴로지는 공개 가능한 원천 자료가 부족해 구체 구성으로 표기하지 않습니다.
