Ownership

직접 담당한 범위

  • 생애설계 목표·콘텐츠 플랫폼의 Express/TypeORM 백엔드 도메인 모델·API·DB 구조 설계
  • 큐레이션 목표·아티클·영상 템플릿과 사용자 목표 인스턴스의 생명주기 분리
  • 템플릿 목표를 사용자 목표로 복제하는 경로와 단순 저장·북마크 연결 경로 분리
  • 목표→태스크→데일리 위계, 8대 영역·세부 카테고리, 해시태그·콘텐츠 그래프 모델링
  • Express 위에서 Router→Controller→Service→Repository→Entity 계층 구조 구성

Constraints

먼저 해결해야 했던 제약

  • 운영자가 편집하는 큐레이션 원본과 사용자가 진행·편집하는 개인 목표는 같은 생명주기를 가질 수 없었습니다.
  • 사용자가 목표를 “시작”하는 행위와 콘텐츠를 “담아두는” 행위는 저장 비용과 최신성 요구가 달랐습니다.
  • 8대 생애 영역과 세부 카테고리는 코드 enum보다 운영 데이터로 관리될 필요가 있었습니다.
  • 아카이브에는 활성 엔티티와 주석 처리된 설계 흔적이 섞여 있어 구현 완료와 미활성 설계를 구분해야 했습니다.
  • 현재 로컬 원본 repo는 단일 merge snapshot만 확인되어 세부 커밋 흐름을 공개 근거로 쓰기 어렵습니다.
  • 배포 파이프라인과 운영 로그는 검증 가능한 자료가 부족해 성과 수치로 사용할 수 없습니다.

Project Overview

큐레이션 콘텐츠를 사용자 목표로 전환하는 데이터 구조를 재설계한 프로젝트입니다

운영자가 만든 목표·아티클·영상을 사용자가 자기 계획으로 가져오되, 원본과 개인 진행 데이터를 분리했습니다.

공개 가능한 원천을 다시 확인한 결과, 이 프로젝트는 오래된 운영 성과보다 템플릿→인스턴스 데이터 모델, 목표 위계, 콘텐츠 그래프, Express 계층 구조를 보여주는 사례로 정리했습니다.

  • 사용자 목표의 기간·예산·완료 상태·하위 태스크를 개인별 데이터로 분리했습니다.
  • 목표 시작은 복제로, 단순 저장은 원본 연결로 구분했습니다.
  • 활성 엔티티, 비활성 설계, 미보유 운영 근거를 구분해 공개했습니다.

Phase 01 · 큐레이션 원본·사용자 데이터 분리

큐레이션 원본·사용자 데이터 분리

Phase 01

운영자 큐레이션 원본과 사용자 진행 데이터를 다른 생명주기로 보았습니다

같은 목표처럼 보여도 운영자가 만드는 추천 목표와 사용자가 실제로 진행하는 목표는 수정 주체, 최신성, 삭제 기준이 다릅니다.

  1. 01

    요구 분석

    운영자는 큐레이션 콘텐츠를 계속 편집하고, 사용자는 이를 개인 목표로 가져와 자기 일정과 진행 상태를 붙입니다.

    • 원본 템플릿이 사용자 편집으로 오염되면 다른 사용자에게도 잘못된 내용이 전파됩니다.
    • 사용자 목표는 기간, 예산, 완료 여부, 하위 태스크처럼 개인별 변경 상태를 가져야 했습니다.
  2. 02

    도메인 모델링

    큐레이션 목표·아티클·영상은 원본 콘텐츠로, 사용자 목표·담아둔 콘텐츠는 사용자 데이터로 분리했습니다.

    • 원본 콘텐츠는 운영자가 관리하고 여러 사용자가 참조합니다.
    • 사용자 데이터는 소유자, 진행 상태, 삭제 여부, 하위 계획을 별도로 가집니다.
  3. 03

    아키텍처 결정

    원본과 사용자 데이터를 같은 테이블에 status로 섞지 않고, 복제와 연결이라는 두 경로로 나눴습니다.

    • 편집 가능한 목표는 복제본이 필요하고, 최신 원본을 보고 싶은 북마크는 연결만으로 충분합니다.
    • 이 구분이 이후 템플릿→인스턴스 모델의 기준이 됐습니다.
  4. 04

    구현·검증

    아카이브된 엔티티와 ADR에서 큐레이션 원본, 사용자 목표, 사용자–콘텐츠 연결 모델을 확인했습니다.

    • 활성 엔티티와 주석 처리된 설계 파일을 나눠 구현 완료 범위를 다시 확인했습니다.
    • 실제 제품명과 내부 API 경로는 공개 copy에서 제거했습니다.
  5. 05

    운영·복구

    데이터가 어긋나면 원본 콘텐츠가 바뀐 것인지, 사용자 복제본이 바뀐 것인지, 단순 연결만 남은 것인지 먼저 구분해야 합니다.

    • 이 구분이 없으면 운영자가 원본을 수정했을 때 사용자 목표까지 의도치 않게 영향을 받을 수 있습니다.
    • 사용자 데이터 삭제는 원본 삭제와 다른 복구 기준을 가져야 합니다.

Project Infrastructure

인프라는 Express 런타임, MySQL, S3 업로드, Docker script 흔적까지만 공개합니다

런타임·저장소·문서화·배포 흔적을 공통 인프라 경계로 정리했습니다.

  1. 01

    런타임

    Node.js/TypeScript와 Express 4 위에 TypeDI service, TypeORM repository, Swagger 문서화 구성이 있습니다.

  2. 02

    상태 저장소

    MySQL과 TypeORM 엔티티가 목표·콘텐츠·분류·사용자 데이터를 담당합니다.

  3. 03

    외부 연동

    JWT·bcrypt 인증, S3 업로드 라이브러리, Swagger, logging/security middleware가 package stack에 남아 있습니다.

  4. 04

    배포 흔적

    Docker build와 ECR push script 흔적은 있으나, 실제 배포 로그·서버 토폴로지·runbook은 확인되지 않습니다.

공개 범위

계정 식별 정보, 운영 데이터, 인증 파일, 운영 로그, 실제 서버 구성은 공개하지 않습니다. 코드와 문서로 확인되는 경계만 사용합니다.

Outcome

확인 가능한 결과

  • 템플릿→사용자 목표 인스턴스 복제와 북마크 연결을 분리한 데이터 모델 정리
  • 목표→태스크→데일리 위계와 카테고리·콘텐츠 그래프 모델링
  • Express/TypeORM/TypeDI 기반 Router→Controller→Service→Repository→Entity 계층 구조 구성
  • 활성 엔티티와 미활성 설계 흔적을 분리해 공개 가능한 구현 범위 정리
  • repo 기간과 snapshot 검증 기준을 분리해 오래된 프로젝트의 과장 위험 축소

Limitations

한계와 미구현 범위

  • 실제 제품명, 비공개 저장소 URL, 운영 데이터, 인증 파일, 내부 API 경로는 공개하지 않습니다.
  • 현재 로컬 원본 repo는 단일 merge snapshot만 확인되어 33 commit 상세 흐름을 재검증하지 못했습니다.
  • 당시 측정 로그가 현재 검증 가능한 원본으로 남아 있지 않아 응답시간·트래픽·장애율 수치는 사용하지 않습니다.
  • 주석 처리된 비전·키워드·자산·리포트 이미지 설계는 구현 완료로 표기하지 않습니다.
  • 배포 파이프라인과 서버 토폴로지는 공개 가능한 원천 자료가 부족해 구체 구성으로 표기하지 않습니다.
Confidentiality

회사명은 공개 가능한 경력 범위에서 사용하지만, 실제 제품명·비공개 저장소·운영 데이터·인증 파일·내부 API는 공개하지 않습니다.
