Process Evidence · 06

운영·복구 기준으로 실패 이후를 검증합니다

실패 지점은 운영자가 볼 수 있는 상태로 남기고, 중복 실행·부분 실패·재처리 기준을 구분했습니다.

멱등키, 행 잠금, outbox, 배치 커서, FAILED/DEAD 상태, runbook을 통해 재실행과 복구 기준을 설계했습니다.

How I worked

실제 작업 방식

  1. Input

    구현 코드, DB 제약, 실패 로그, 배치 커서, 큐 상태, 운영 재처리 조건을 함께 확인했습니다.

  2. Question

    중복 실행, 부분 실패, 배포 중단, 외부 서비스 장애 이후에도 같은 결과로 복구되는지 확인했습니다.

  3. Output

    멱등키, 행 잠금, outbox, cursor, FAILED/DEAD 상태, 재처리 SQL, 큐 backlog 진단, stale recovery 기준을 남겼습니다.

수집 근거

운영 근거를 실패 상태·재처리 단위·직접 기여 범위로 분류

운영·복구 카드에는 정상 성공보다 멈춘 위치가 어떤 상태로 남는지, 어떤 단위로 재실행할 수 있는지, 그 구현이 내 직접 기여 범위 안에 있는지를 증명하는 자료를 모았습니다.

복구 회고
Outbox/NotificationDelivery 복구, Transactional Outbox 2단계 재시도, PG 승인 후 DB 확정 실패 복구, self-rescheduling 정산 배치, 온체인 커서 배치 회고를 연결했습니다.
런북
DEAD record, queue backlog, stale ENQUEUED/SENDING, Notification DEAD, retry-to-PENDING 절차가 문서화된 runbook을 복구 기준으로 사용합니다.
코드 근거
Outbox retry/dead repository, BullMQ publisher/consumer, settlement batch run/reschedule/reset stale, subscription renewal finalize retry handler를 구현 근거로 대조했습니다.
제외 기준
Routine/Daily row는 작업 추적 근거로만 두고, 실제 운영 복구 주장은 runbook·코드·회고가 함께 있는 경우에만 사용합니다.
상세 작업 사례

멈춘 지점을 상태와 로그로 남겨 재실행 가능하게 검증

구현 이후에는 정상 성공만 보지 않고, 중복 실행·부분 실패·큐 적체·배치 중단 이후 운영자가 어떤 상태를 보고 무엇을 재실행할 수 있는지 확인했습니다.

실제 구현으로 이어진 위치

  • 포인트 회계·보상 시스템

    Outbox/Queue 인시던트 runbook에서 DEAD 레코드, backlog, stale ENQUEUED/SENDING, Notification DEAD를 각각 증상·진단·복구 절차로 나눴습니다.

    Outbox·알림 복구 경계 보기
  • 6.7억+ 온체인 트랜잭션 보상·통계 파이프라인

Input

Failure Case
중복 실행, 부분 실패, 배포 중단, 외부 서비스 장애, queue backlog, stale 상태가 생겼을 때 어느 레코드가 복구 기준인지 확인했습니다.
Recovery
전체 일괄 재처리 대신 타입별 DEAD 복구, 내부 finalize retry, cursor 기반 재시작처럼 실패 범위에 맞는 복구 경로를 나눴습니다.
Output
멱등키, 행 잠금, outbox, cursor, FAILED/DEAD 상태, 재처리 SQL, 큐 backlog 진단, stale recovery 기준을 남겼습니다.
검증 기준

운영 복구와 직접 기여 범위를 함께 확인 가능

운영 가능성은 패턴 이름만으로 주장하지 않고, 어떤 상태를 보고 어떤 재처리를 할지와 해당 구현의 직접 기여 범위를 함께 남겼습니다.
