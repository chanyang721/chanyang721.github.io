Process Evidence · 03

아키텍처 경계와 불변 조건을 결정합니다

같이 확정할 상태와 비동기로 넘길 처리를 나누고, 재시도·중복·부분 실패를 흡수할 경계를 정했습니다.

도메인 모델을 만든 뒤에는 트랜잭션 안에서 보장할 사실, Outbox 이후 재시도할 일, 외부 공급자 실패와 별도로 남길 상태를 구분했습니다.

How I worked

실제 작업 방식

  1. 입력

    도메인 모델, 상태 전이, PG·FCM·큐·배치 같은 외부 시스템의 실패 특성, 운영자가 대사해야 하는 데이터를 함께 봤습니다.

  2. 확인 질문

    어떤 상태는 같은 DB 트랜잭션에서 확정해야 하는지, 어떤 작업은 실패해도 재시도하면 되는지, 어떤 값이 정본인지 물었습니다.

  3. 산출

    트랜잭션 경계, 추가 전용 원장, Outbox 저장 지점, 공급자 어댑터, 알림 전달, 복구 상태를 아키텍처 결정으로 남겼습니다.

수집 근거

아키텍처 판단 근거를 트랜잭션·정본 상태·실패 격리로 분류

수집한 회고와 코드/docs를 아키텍처 카드에 넣을 때는 패턴 이름을 나열하지 않고, 어떤 상태를 같은 트랜잭션에서 확정하고 어떤 일을 재시도 가능한 후속 처리로 분리했는지 기준으로 정리했습니다.

B2B 경계
승인 요청, 심사자 판단, 승인·반려 이력, 현재 소속·역할 반영은 서로 다른 책임이므로 경계 판단 샘플로 사용합니다.
가격·결제
클라이언트 금액을 신뢰하지 않고 정책 계산 근거를 주문에 동결한 회고, 가격 정책 ADR, 장바구니/주문 서버 재계산 문서를 연결했습니다.
비동기·복구
Transactional Outbox, Dual Queue Notification, PG 이후 내부 확정 재시도, Outbox · NotificationDelivery 복구 회고를 실패 격리 근거로 묶었습니다.
정책·회계
정책 기반 티어, 유료·무료 자산 분리, 추가 전용 원장, 지역 고정 전략 ADR은 코드 배포 없이 바뀌는 정책과 금전성·권역 불변 조건의 근거로 사용합니다.
상세 작업 사례

B2B 승인 흐름에서 상태 전이와 감사 경계를 먼저 고정

비공개 B2B 플랫폼 분석에서는 신청, 심사, 승인, 반려, 카테고리 검토를 단순 관리자 액션이 아니라 상태 전이와 감사 기록이 필요한 workflow로 나눴습니다.

실제 구현으로 이어진 위치

  • 포인트 회계·보상 시스템

    금전성 상태는 Ledger와 Wallet 트랜잭션으로 확정하고, 보상 이벤트와 알림 전달은 Outbox · NotificationDelivery 경계로 분리했습니다.

    도메인 이벤트와 알림 전달 경계 보기
  • 멀티 PG·구독 결제 시스템

    PG별 반환·콜백 차이를 어댑터와 핸들러에 가두고, 구독 활성화·갱신 확정은 프로세서의 상태 전이로 모았습니다.

    PG 라우팅과 도메인 상태 수렴 보기
경계
사용자 소속·역할의 현재 상태와 인증 요청·승인 이력은 변경 이유가 다르므로 분리했습니다.
불변 조건
승인·반려는 현재 상태만 바꾸는 액션이 아니라 누가 어떤 근거로 상태를 바꿨는지 설명 가능한 기록을 남겨야 합니다.
활용 범위
이 B2B 샘플은 운영 안정성보다 Step 01-03의 분석·모델링·계약화 근거로 사용하고, 실제 운영 복구 근거는 실서비스 프로젝트로 연결합니다.
검증 공백
승인과 소속·역할 생성을 원자화하려는 의도는 확인되지만, 행 잠금·조건부 갱신·도메인 범위 검증·고유 제약 근거는 부족해 “정확히 한 번” 승인 사례로는 쓰지 않습니다.
