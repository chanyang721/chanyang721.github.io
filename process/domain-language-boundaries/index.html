Process Evidence · 02

도메인 언어·경계·상태 모델을 잡습니다

결제, 청구, 수강권, 구독, 환불, 포인트 같은 용어가 코드와 문서에서 같은 의미로 쓰이도록 경계와 상태 모델을 정리했습니다.

기능 단위가 아니라 Order, PaymentIntent, Payment, Entitlement, Subscription, Ledger 같은 도메인 객체와 상태 전이로 시스템을 나눴습니다.

How I worked

실제 작업 방식

  1. 입력

    요구사항 문서, 기존 DB, 결제·구독 코드에서 반복되는 명사와 생명주기가 다른 상태 변경 지점, 언어·통화처럼 글로벌 확장 때 바뀌는 축을 모았습니다.

  2. 확인 질문

    현재 상태와 과거 사실이 섞였는지, 외부 부수효과가 내부 의도보다 먼저 실행되는지, 접근 권한을 주문의 부속값처럼 다루는지 확인했습니다.

  3. 산출

    구매, 청구 회차, 결제 시도, 실제 결제, 수강권, 원장, pending/final 상태를 분리한 도메인 모델로 고정했습니다.

수집 근거

도메인 모델링 근거를 B2B 감사·회고·프로젝트 아카이브로 정규화

수집한 자료 중 도메인 모델링 카드에는 명사 목록이 아니라 생명주기, 소유권, 현재 상태와 과거 사실의 분리를 설명할 수 있는 근거만 남겼습니다.

B2B 모델
행위자·소속·역할 승인 모델 감사, Company · Vendor, 사용자 도메인, Tax ↔ UI Category, VendorStaff, Attachment 회고를 B2B 모델링 근거로 묶었습니다.
실서비스 모델
구매 사실·시청 권한·구독 정책·시청 이력을 분리한 Entitlement 회고, 언어별 카탈로그 분류와 Accrual · Ledger · Wallet 회고를 대표 검증 근거로 연결했습니다.
보조 사례
eCRF 6개 책임 경계, 지오펜스·AR 커머스, 템플릿에서 인스턴스로 이어지는 콘텐츠, Firestore 내장 값 객체는 같은 모델링 습관의 보조 사례로만 사용합니다.
한계 표시
본문이 비어 있는 관계 기록이나 Study Room 학습 기록은 직접 근거로 쓰지 않고, 코드·문서·회고로 확인되는 자료만 카드 문구에 반영합니다.
상세 작업 사례

권한·소속·심사·카테고리를 별도 도메인으로 분리

비공개 B2B 플랫폼에서 Company, Vendor, UserAffiliation, UserRole, CertificationRequest, TaxCategory, UICategory를 분리했습니다. 사용자 한 명이 여러 조직 소속과 역할을 가질 수 있고, 기업·제휴처·사원 인증은 각각 다른 승인 생명주기를 갖는 모델로 정리했습니다. 후속 감사에서는 이 모델 의도가 실제 코드 계약과 어긋난 지점도 분리해 기록했습니다.

실제 구현으로 이어진 위치

  • 포인트 회계·보상 시스템

    지급 예정, 불변 원장, 현재 잔액을 Accrual, Ledger, Wallet으로 분리해 현재 상태와 과거 사실의 경계를 나눴습니다.

    Accrual · Ledger · Wallet 모델 보기
  • 포인트 회계·보상 시스템 · 글로벌 카탈로그 기준

    상품 표시 언어, 카테고리 코드와 번역, 주문 통화, 알림 대체 문구를 분리해 표시 언어와 회계·결제 기준이 섞이지 않게 했습니다.

    언어·카테고리 모델 보기
  • 멀티 PG·구독 결제 시스템

    영상·구독 접근 정책은 ProductVideo, SubscriptionProduct, Access Policy로 나누고, 결제 상태는 Order, SubscriptionInvoice, PaymentIntent, Payment로 분리했습니다.

    영상·구독·결제 모델 보기
입력
행위자별 기획서와 인증·권한·카테고리 요구에서 반복되는 명사, 상태, 승인 주체를 추렸습니다.
경계
회원 자체 정보, 조직 소속, 도메인별 역할, 인증 요청, 세무 카테고리, 화면 노출 카테고리를 서로 다른 변경 이유를 가진 모델로 분리했습니다.
상태 모델
기업·제휴처·사원 인증은 현재 소속 정보가 아니라 요청, 승인, 반려 이력을 갖는 별도 대기 사실로 보았습니다.
산출
이후 API와 DB가 화면 메뉴가 아니라 Identity, Affiliation, Certification, Taxonomy 경계를 기준으로 나뉘도록 정리했습니다.
감사
사원 승인 흐름은 소속과 역할 생성을 같은 트랜잭션으로 묶으려는 의도가 확인되지만, 엔티티·서비스 필드 불일치와 권한 guard 계약 불일치가 있어 완성된 RBAC 사례로 과장하지 않습니다.
검증 기준

모델 이름보다 각 모델이 지키는 불변 조건을 함께 정리

포트폴리오에는 전체 테이블 컬럼을 공개하지 않고, 모델이 대답해야 하는 질문과 깨지면 안 되는 조건을 공개 가능한 수준으로 남겼습니다.

결제·구독
Order는 구매 의도, Invoice는 청구 회차, Intent는 PG 시도, Payment는 실제 승인 결과를 담당하도록 분리했습니다.
포인트·원장
Accrual은 지급 약속, Ledger는 append-only 변경 근거, Wallet은 현재 잔액 스냅샷으로 나눴습니다.
글로벌 표시
분류 code와 locale별 표시명, 약관 번역, 결제 통화, 알림 메시지 선택을 분리해 화면 언어와 서버 정본을 같은 모델에 섞지 않았습니다.
공개 범위
실제 테이블 전체 구조 대신 책임, 상태 전이, 불변 조건만 공개해 회사 내부 스키마 노출 없이 설계 판단을 설명합니다.
