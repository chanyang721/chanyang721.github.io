Process Evidence · 05

품질 속성에 맞는 인프라 옵션을 선택합니다

실행 시간, 실패 비용, 재시도 가능성, 관측성, 비용 조건을 보고 인프라 구성을 판단했습니다.

도메인 플로우의 성격에 따라 동기 API, worker, object storage, Redis, CloudWatch, 배포 경계를 나눴습니다.

How I worked

실제 작업 방식

  1. Input

    실행 시간, 파일 크기, 장애 전파 범위, 무중단 제약, 비용 조건, 배포 도구가 만든 산출물과 사람이 관리할 소스 자원을 함께 확인했습니다.

  2. Question

    API 서버가 직접 처리해야 하는지, queue/worker나 외부 저장소 어댑터로 분리해야 하는지, 어떤 자원을 코드의 책임으로 둘지 판단했습니다.

  3. Output

    비동기 처리 위치, object storage 책임, ASG/CodeDeploy/IaC 책임 경계, 로그·runbook 관측 기준을 정리했습니다.

수집 근거

인프라 근거를 실행 특성·배포 안전성·관측 가능성으로 선별

인프라 카드에는 기술 스택 목록보다 실행 시간이 길거나 실패 전파 비용이 큰 흐름을 어디에 배치했는지, 배포 중 어떤 상태를 보고 복구할 수 있는지를 보여주는 근거만 남겼습니다.

운영 문서
실서비스 문서에서 CodeDeploy, 배포 오케스트레이션, DR, SLO, Outbox runbook, CloudWatch·ALB health check, 장기 region-affinity 전략 기준을 확인했습니다.
배포 판단
CI/CD 분리, production CodeDeploy 전환, OIDC 마이그레이션 경로, brownfield IaC 정리 회고를 배포 안전성 근거로 묶었습니다.
비동기 실행
CSV ingestion, Firebase/Cloud Functions, queue/worker, 외부 저장소 어댑터 같은 자료는 요청-응답 경계 밖으로 분리한 보조 사례로 사용합니다.
수치 제한
접근 가능한 로그로 검증하지 못한 p95, uptime, RPS, TPS, 비용 수치는 만들지 않고 문서·코드로 확인되는 운영 기준만 사용합니다.
상세 작업 사례

도메인 플로우의 실행 특성에 맞춰 인프라 경계를 선택

요구사항이 만드는 실행 시간을 보고 동기 API, 비동기 worker, 파일 처리, 배포 자원, 관측 기준을 나눴습니다. 빠르게 응답해야 하는 요청과 오래 걸리거나 재시도 가능한 작업을 같은 실행 경계에 묶지 않았습니다.

실제 구현으로 이어진 위치

  • 멀티 PG·구독 결제 시스템

    동기 결제 API, 구독 갱신 worker, Redis/BullMQ, PostgreSQL, PG callback, CodeDeploy 배포 확인을 서로 다른 실행 책임으로 나눴습니다.

    결제 런타임 구조 보기
  • 포인트 회계·보상 시스템

    API, worker, Redis/BullMQ, PostgreSQL, CodeDeploy, CloudWatch의 실행 책임을 나누고 운영 중인 Blue/Green 자원을 코드화하는 경계를 정했습니다.

    인프라 아키텍처 보기
  • 온체인 통계 데이터 파이프라인

    사용자 API, 어드민 승인 흐름, 통계 배치를 독립 실행 단위로 나누고 Redis 락·커서 체크포인트로 배치 재실행 기준을 만들었습니다.

    배치 실행 구조 보기
  • 콘텐츠 SaaS 운영 백엔드

    위치기반 AR 커머스의 Firebase·MongoDB·S3 같은 외부 인프라 경계와 공개 가능한 배포 근거의 한계를 분리했습니다.

    초기 인프라 경계 보기
  • 레거시 도메인 리뉴얼

    생애설계 콘텐츠 리뉴얼은 Docker/ECR 스크립트 흔적과 마이그레이션 전환 근거는 있지만, 배포 로그와 서버 토폴로지는 근거 부족으로 한계 표시했습니다.

    전환·배포 한계 보기
  • Evidence-driven Engineering Portfolio

    Next.js 정적 라우트, sitemap/robots, lint/typecheck/build/check를 공개 전 검증 경계로 두었습니다.

    포폴 배포 검증 보기
Input
실행 시간, 파일 크기, 장애 전파 범위, 무중단 제약, 비용 조건, 배포 도구가 만든 산출물과 사람이 관리할 소스 자원을 함께 봤습니다.
Decision
즉시 응답이 필요한 요청은 API 서버에 두고, 재시도 가능한 후속 작업은 worker/queue로, 파일·첨부 저장은 외부 저장소 어댑터로 분리했습니다.
Boundary
운영 중인 Blue/Green 환경에서는 배포 도구가 생성하는 산출물과 코드가 소유해야 하는 원본 자원을 분리해 판단했습니다.
Output
비동기 처리 위치, object storage 책임, ASG/CodeDeploy/IaC 책임 경계, 로그·runbook 관측 기준을 정리했습니다.
검증 기준

운영 검증 기준과 측정 가능한 지표를 구분

인프라와 운영 자료에는 CloudWatch, ALB health check, runbook, 배포 경계처럼 운영 가능성을 판단한 기준이 있습니다. 반대로 접근 불가능한 운영 p95·오류율은 임의 수치로 만들지 않고 공개 가능한 확인 기준만 사용합니다.

운영 기준
ALB/ASG/CodeDeploy/CloudWatch, Outbox runbook, SLO 문서로 헬스체크·로그·재처리 기준을 정리했습니다.
측정 가능
월 포인트 정산은 운영 중 확인한 대략치로, 검색 창·chunk 크기·갱신 실패 횟수는 문서·코드로 확인 가능한 값만 표기합니다.
측정 불가
현재 접근할 수 없는 AWS 운영 로그 기반 p95, 오류율, uptime은 성과 수치로 표기하지 않습니다.
