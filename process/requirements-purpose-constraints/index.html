Process Evidence · 01

요구사항을 목적·행위·제약으로 분류합니다

기능명을 바로 API로 옮기기 전에 필요한 이유, 실행 주체, 상태 변화, 정책·예외·운영 조건을 분리했습니다.

서비스 담당자와 도메인 문서에서 나온 요구사항을 기능 목록이 아니라 목적, 행위자, 상태 변화, 정책·운영 제약으로 먼저 쪼갰습니다.

How I worked

실제 작업 방식

  1. 입력

    서비스 담당자, 도메인 마스터, 기획 문서, 운영 정책, 화면 흐름, 기존 코드와 DB 구조에서 나온 요구사항을 한곳에 모았습니다.

  2. 확인 질문

    각 요구가 어떤 비즈니스 목적을 해결하는지, 누가 실행·승인·조회하는지, 어떤 상태가 바뀌는지, 어떤 정책과 실패 비용을 갖는지 먼저 물었습니다.

  3. 산출

    행위자별 책임, 상태 변화, 정책 제약, 예외 케이스를 분리하고 이후 도메인 모델·유스케이스·API 계약으로 이어질 분석 단위로 정리했습니다.

수집 근거

요구 분석 근거를 행위자 기획서·유스케이스 기록·실서비스 문서로 대조

원천 작업 기록과 로컬 아카이브를 함께 확인해, 요구 분석 카드에는 “무엇을 만들었나”보다 “왜 필요했고, 누가 상태를 바꾸며, 어떤 제약을 지켜야 했나”를 보여주는 근거만 남겼습니다.

B2B 샘플
비공개 B2B 플랫폼의 행위자별 기획서, 상위 스펙 검토 작업, 승인·정산·카테고리 요구를 요구 분류 샘플로 사용합니다.
반복 습관
과거 도메인·유스케이스 기록에는 관계도, 시퀀스 다이어그램, 성공·예외 시나리오, 테스트 케이스, 입출력 인터페이스를 먼저 쓰는 작업 기록이 남아 있습니다.
실서비스 대조
결제·구독·환불·장바구니 문서는 화면 요구를 미리보기, 주문, 결제 시작, 콜백, 상태 조회, 서버 재검증으로 나눈 근거입니다.
글로벌 조건
대표 교육 콘텐츠 서비스에서는 언어, 국가, 통화, 법적 기준을 요구 제약으로 분리해 카탈로그 표시, 약관 동의, 결제 통화, 알림 문구가 같은 기준을 참조하게 했습니다.
제외 기준
Routine/Study Room은 판단 출처나 학습 기록으로만 쓰고, 요구 분석 카드의 직접 근거로 과장하지 않습니다.
검증 기준

원천 요구가 어떻게 모델과 유스케이스로 바뀌었는지 추적 가능하게 남김

단건 결제, 최초 구독 결제, 환불, 영상 접근 권한 문서에는 화면 흐름을 그대로 API 목록으로 옮기지 않고 목적, 서버 정본, 상태 변경, 예외 케이스, 프론트 표시 기준을 함께 정리한 흔적이 남아 있습니다.

요구 원문
결제하기, 구독 시작, 환불 가능 여부, 수강 가능 여부처럼 화면에서 보이는 요구를 출발점으로 삼았습니다.
분류 결과
구매 의도, PG handoff, 서버 재검증, 권한 부여, 환불 실행을 서로 다른 책임과 상태 변경으로 나눴습니다.
포폴 노출 방식
원천 요구가 어떤 분석 단위를 거쳐 도메인 모델과 유스케이스로 바뀌었는지 공개 가능한 수준의 판단 흐름으로 재구성했습니다.
상세 작업 사례

B2B 플랫폼 요구를 행위자와 운영 책임으로 분류

비공개 B2B 플랫폼 분석에서는 기능 목록을 그대로 백로그로 옮기지 않고, 행위자별 기획서·상위 스펙 작업과 백엔드 커밋 이력을 맞춰 보며 목적·권한·상태 변화·운영 책임을 먼저 분리했습니다.

실제 구현으로 이어진 위치

  • 멀티 PG·구독 결제 시스템 · 결제·구독 요구사항 케이스 맵

    이 프로젝트에서는 영상 접근, 단건 결제, 최초 구독 결제, 정기 갱신, 플랜 변경·해지를 같은 요구사항 큐에 놓고 각각 목적, 상태 변화, 서버 정본, 복구 지점이 다른 케이스로 분석했습니다.

    결제·구독 요구사항 케이스 보기
  • 포인트 회계·보상 시스템

    “환불 가능 여부 확인”은 UX 판단으로 두고, 실제 환불 실행은 원거래·소유권·정책·사용 이력·복원 대상을 다시 계산하는 상태 변경 유스케이스로 분리했습니다.

    포인트 사용·환불 흐름 보기
입력
플랫폼 운영자, 기업 관리자, 직원, 제휴처/소상공인 기획서와 MVP 우선순위, MVP 페이지 구성, 카테고리 설계안, 정산·세금계산서 요구를 함께 놓고 읽었습니다.
분류
운영자는 심사·정산·노출 제어, 기업 관리자는 소속 직원과 복지금 설정·보고, 직원은 인증·예약·이용, 제휴처는 입점·카테고리·예약·정산 이력을 책임지는 행위자로 나눴습니다.
상태 변화
가입 승인, 사원 인증 요청, 제휴처 인증, 카테고리 승인, 정산 예정·완료, 세금계산서 발행을 각각 PENDING, APPROVED, REJECTED 같은 처리 상태가 필요한 흐름으로 분리했습니다.
산출
이 분류를 바탕으로 Company, Vendor, UserAffiliation, UserRole, CertificationRequest, TaxCategory, UICategory 모델과 인증·승인·반려 유스케이스를 도출했습니다.
추적 근거
백엔드 인수인계 문서와 원천 작업 기록으로 확인한 Service Build/Routine 관계에는 기획서 분석, Domain 모델링, 전체 관계도, Usecase, 시퀀스 다이어그램, 비즈니스 플로우까지 이어진 분석 흔적이 남아 있습니다.
커밋 근거
Git 이력에서는 도메인·역할·소속 모델 방향과 사원 인증 흐름이 컨트롤러, DTO, 서비스, 엔티티, 팩토리, 리포지토리, Swagger 문서까지 연결된 변경으로 확인됩니다.
한계
이 샘플은 요구 분석과 모델링 근거로 사용합니다. 런타임 승인 성공, 동시성 안전성, 운영 복구까지 완료된 실서비스 근거로는 사용하지 않습니다.
