Process Evidence · 04

유스케이스·계약·코드 검증으로 연결합니다

도메인 모델을 실제 API, DTO, sequence diagram, 서버 재검증 기준으로 고정했습니다.

preview, order, payment start, confirm, callback, polling 같은 유스케이스를 나누고 각 단계의 검증 조건을 문서화했습니다.

How I worked

실제 작업 방식

  1. Input

    사용자 시나리오, PG return/callback 흐름, 프론트 필요 응답, 운영자가 확인해야 하는 상태를 한 흐름으로 놓고 검토했습니다.

  2. Question

    각 API가 어떤 유스케이스를 끝내는지, 어떤 값은 힌트이고 어떤 값은 서버가 재계산해야 하는지, 어떤 상태가 acceptance 기준인지 나눴습니다.

  3. Output

    sequence diagram, DTO, endpoint 순서, error response, 미구현 범위, 서버 재검증 조건을 같은 문서 안에 남겼습니다.

수집 근거

구현 근거를 API 계약·레이어 연결·테스트·감사 결과로 나눠 확인

수집한 구현 자료는 “코드가 있다”가 아니라 요구 분석 결과가 controller, DTO, service, factory, repository, worker, 테스트와 한 줄로 이어지는지 기준으로 정제했습니다.

B2B 코드 연결
사원 인증 flow와 기업·제휴처 인증, 카테고리 모듈은 actor 요구가 controller, DTO, service, entity, factory, repository, Swagger, test로 이어지는 샘플입니다.
검증된 한계
같은 B2B 샘플에서 build 통과와 런타임 계약 검증은 분리합니다. field drift, guard metadata mismatch, 동시 승인 안전성 부족은 성공 사례가 아니라 감사 결과로 표시합니다.
실서비스 코드
결제·구독 프로젝트에서는 cart price quote, order price snapshot, Entitlement factory/service, subscription finalize retry handler를 구현 근거로 연결했습니다.
대표 검증
보상 회계 프로젝트에서는 rewards facade, settlement batch, accrual·ledger·wallet service, notification delivery 흐름을 실행 순서와 회귀 테스트 기준으로 확인했습니다.
상세 작업 사례

인증·승인·반려 흐름을 API 계약과 테스트 단위로 연결

비공개 B2B 플랫폼에서 기업 인증 요청, 사원 인증 승인·반려, 제휴처 카테고리 승인 흐름을 controller, service, repository, factory, DTO, Swagger 문서와 테스트 단위로 연결하려 했습니다. 후속 코드 감사에서는 build 통과와 런타임 계약 검증을 분리해, 성공 주장 대신 검증 기준의 빈틈까지 남겼습니다.

Input
actor별 화면 흐름과 승인/반려 정책을 API 요청, 응답, 권한 조건, 예외 케이스로 풀었습니다.
Contract
controller와 DTO는 외부 계약을, service는 유스케이스 실행 순서를, factory와 repository는 도메인 객체 생성과 저장 책임을 갖도록 나눴습니다.
Verification
Swagger 문서와 controller/service/factory 테스트가 같은 유스케이스 이름과 상태 전이를 검증하도록 맞췄습니다.
Output
요구사항이 API 엔드포인트 목록에서 끝나지 않고 sequence, DTO, response, 실패 조건, 테스트 단위까지 이어지게 했습니다.
Caveat
이 샘플은 분석 산출물이 코드 레이어로 연결되는 방식을 보여주되, 실제 DB 실행·권한 평가·동시 승인 안전성은 미검증 또는 결함 확인 상태로 표시합니다.
검증 기준

분석 산출물이 API 계약과 수락 기준으로 이어졌는지 확인 가능

결제·구독 use-case 문서에는 endpoint 순서, DTO, 응답 표시 기준, 에러 조건, 프론트가 믿어도 되는 값과 서버가 다시 확정해야 하는 값을 나눠 둔 근거가 있습니다.

실제 구현으로 이어진 위치

  • 멀티 PG·구독 결제 시스템 · 정책 경계

    갱신 실패, 플랜 변경, 해지, 접근 권한에서 구현된 상태 정책과 환불·proration처럼 분리해 둔 미구현 범위를 함께 확인할 수 있습니다.

계약
주문 생성, 결제 시작, confirm, callback, polling처럼 유스케이스별 endpoint와 응답 기준을 분리했습니다.
검증
같은 멱등키·다른 payload, 권한 없음, PG callback 지연, confirm 순서 역전 같은 실패 조건을 문서와 테스트 기준으로 남겼습니다.
한계
구독 환불과 일부 proration 정책처럼 최종 구현 범위에 들어가지 않은 항목은 미구현으로 별도 표시했습니다.
